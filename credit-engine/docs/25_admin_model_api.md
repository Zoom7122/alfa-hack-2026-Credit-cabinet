# Административный API моделей

Контракт: [admin.openapi.json](../contracts/admin.openapi.json), OpenAPI 3.1. Запуск и аутентификация описаны в [доступе к админке](24_admin_access.md). Все маршруты ниже требуют браузерную сессию. `POST`, `PUT`, `DELETE` дополнительно требуют точный `Origin` и `X-CSRF-Token`; Bearer МС2 не заменяет сессию.

Префикс — `/api/admin/v1`. Автор всегда берётся из сессии, поле `author` от клиента не принимается. Для изменений обязательно непустое `reason` до 16 KiB UTF-8. Ошибочные бизнес-настройки черновика сохранять можно; технический формат JSON должен соответствовать [формату модели](10_model_format.md). Успешное сохранение черновика не означает готовность к выпуску.

## Маршруты

| Метод и путь | Назначение |
|---|---|
| `GET /models` | Опубликованные неизменяемые версии. |
| `GET /models/{version}` | Определение и контрольные суммы конкретной версии. |
| `POST /models/{version}/drafts` | Копия опубликованной модели: `new_version`, `reason`; 201 и `Location`. |
| `GET /drafts` | Текущие неудалённые черновики. |
| `POST /drafts` | Новый черновик: `definition`, `reason`; 201 и `Location`. |
| `GET /drafts/{id}` | Определение текущей ревизии. |
| `PUT /drafts/{id}` | Сохранение: `expected_revision`, `definition`, `reason`; 200. |
| `DELETE /drafts/{id}` | Логическое удаление: `expected_revision`, `reason`; 204. |
| `GET /drafts/{id}/validation` | `draft_id`, точная `revision`, SHA определения и полный `validation` общего валидатора. |
| `GET /drafts/{id}/revisions` | Неизменяемые ревизии, в том числе после удаления черновика. |
| `GET /drafts/{id}/revisions/{revision}` | Точное историческое определение. |
| `POST /compare` | Сравнение двух точных ссылок `left`, `right`. |
| `GET /history/{kind}/{id}` | Автор, время, основание, состав изменений; `kind` — `DRAFT`, `MODEL`, `RELEASE`. |
| `GET /releases` | Метаданные подготовленных релизов без архивов. |
| `GET /releases/{version}` | Метаданные одного релиза, манифест и контрольные суммы. |
| `POST /releases/preview` | Предварительная проверка и diff без сохранения; [описание выпуска](31_simulation_release_ui.md). |
| `POST /releases` | Подготовка комплекта: `release`, `reason`; 200 при подготовке и идентичном повторе. |
| `GET /releases/{version}/archive` | Неизменяемый ZIP; `Content-Disposition`, `X-Archive-SHA256`, `ETag`. |

Списки принимают только `limit` (1–200, по умолчанию 50) и `offset` (от 0, по умолчанию 0). Ответ — JSON-массив в порядке репозитория. Повторные, неизвестные и некорректные query-параметры отклоняются.

JSON-ключи чувствительны к регистру; дубли, неизвестные поля и null обязательных значений не принимаются. Определение ограничено 4 MiB, весь запрос — 4 MiB + 32 KiB. Нужен `Content-Type: application/json`. Дополнительные флаги обхода проверки, подмена автора или прямое изменение опубликованной версии не предусмотрены.

## Ревизии и валидация

`expected_revision` — положительное целое число. При устаревшей ревизии сервер возвращает 409 `REVISION_CONFLICT` с `current_revision`. Необходимо прочитать актуальный черновик и разрешить конфликт перед повторным сохранением. Конкурентное изменение или удаление не перезаписывает чужую ревизию.

Проверка черновика использует `model.Validate` и доверенный каталог источников, как генератор/CLI. Ответ включает ошибки с путями JSON Pointer, максимумы анкеты, дополнительных критериев и общую сумму. Публикация запускает ту же проверку повторно по зафиксированным версиям/заблокированным ревизиям внутри транзакции. При `MODEL_VALIDATION_FAILED` ответ 422 содержит `model_version` и полный `validation`.

Строго проверяются все ограничения общего валидатора, включая 750/250/1000. Общая сумма 1000 при неправильном распределении блоков также блокирует выпуск. Промежуточный черновик с 999 или 1001 баллом сохраняется и показывает ошибку; опубликованная модель и архив при таком запросе не создаются.

## Сравнение

```json
{
  "left": {"kind": "PUBLISHED", "id": "ip-v2", "revision": null},
  "right": {"kind": "REVISION", "id": "<draft UUID>", "revision": 3}
}
```

Для опубликованной модели `id` — версия, `revision` обязательно null. Для черновика требуется конкретная историческая ревизия; скрытого выбора latest нет. Сравнение разных типов заёмщика отклоняется. Ответ включает обе ссылки и `comparison`: SHA канонических определений и отсортированные `changed_paths`. Порядок правил/массивов и точные числовые литералы сохраняются; `0` и `0e0` различаются. Сравнение не меняет модели, не считает кредит и не обращается к МС2; расчётная симуляция — [отдельная операция](27_simulation.md).

## Подготовка комплекта

```json
{
  "release": {
    "version": "2.1.0",
    "base_version": "2.0.0",
    "published_versions": ["ip-v2", "legal-v2"],
    "drafts": [{"id": "<draft UUID>", "revision": 3}],
    "notes": "Описание изменения"
  },
  "reason": "Основание подготовки"
}
```

Запрос задаёт полный каталог нового релиза, точный базовый релиз и ожидаемые ревизии выбранных черновиков. Прочие черновики не подмешиваются. Генератор формирует определения, Go-код, DTO, OpenAPI, таблицы Markdown, описание изменений, манифест и суммы. Результат и история сохраняются одной транзакцией; сервер не записывает комплект в рабочие файлы репозитория.

Идентичный повтор возвращает тот же архив и не дублирует историю. Изменение содержимого уже опубликованной версии/схемы или подготовленного релиза получает 409 `IMMUTABLE_VERSION`. Новые версии в БД не активируют МС1: применение архива и пересборка остаются отдельным действием. Рабочий МС1 продолжает использовать свой скомпилированный каталог.

Подготовка выполняется в контексте запроса. Стандартный бюджет админки — 30 секунд на операцию и 45 секунд на HTTP-ответ; он учитывает проверку и генерацию полного каталога. Настройки описаны в [доступе к сервису](24_admin_access.md). При отмене/истечении контекста транзакция не подтверждает частичный релиз.

## Ошибки

Ответы ошибок — `application/problem+json`. Основные коды: 400 — неверная форма запроса, 401/403 — доступ/CSRF, 404 — объект отсутствует, 409 — конфликт/неизменяемость, 413 — размер, 415 — формат тела, 422 — некорректные административные данные/бизнес-валидация, 503 — БД недоступна, 504 — deadline запроса. Исходные сообщения БД и секреты не возвращаются.

Изолированные тесты проверяют защиту всех маршрутов, формат, лимиты, ошибки и соответствие контракта маршрутам. PostgreSQL HTTP-проверки под тегом `integration` проходят реальный вход, черновики с неверными весами, отказ выпуска, CAS/конкурентное редактирование, сравнение, историю, неизменяемую публикацию, повтор, скачивание архива и удаление с сохранением ревизий.
