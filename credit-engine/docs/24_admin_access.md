# Запуск и доступ к административному сервису

`cmd/admin-service` — третий сервис на Gin. Конструктор собирает зависимости без сетевых обращений. Перед открытием HTTP-порта процесс проверяет соединение с PostgreSQL и состояние собственных миграций, затем идемпотентно импортирует встроенный базовый релиз `2.0.0`. Применять миграции нужно отдельно через `cmd/admin-migrate`: сервер не выполняет DDL. Остановка по SIGINT/SIGTERM прекращает HTTP-обслуживание с бюджетом 5 секунд и закрывает пул БД.

## Настройки

| Переменная | Значение / назначение |
|---|---|
| `ADMIN_ADDR` | `:8084`. |
| `ADMIN_DATABASE_URL` | Обязательная строка подключения PostgreSQL; собственная схема описана в [описании БД](22_admin_database.md). |
| `ADMIN_USERNAME` | Одна административная учётная запись, непустая, до 256 байт. |
| `ADMIN_PASSWORD_HASH` | Обязательный bcrypt-хеш, cost 10–14. Исходный пароль не хранится. |
| `ADMIN_EVENTS_TOKEN` | Обязательный отдельный секрет МС2; 32–256 печатных ASCII-символов без пробелов. МС2 получает то же значение. |
| `ADMIN_PUBLIC_ORIGIN` | Точный внешний origin интерфейса, например `https://admin.example`; без пути, query и credentials. По умолчанию `http://localhost:8084`, для него требуется явный `ADMIN_COOKIE_SECURE=false`. |
| `ADMIN_COOKIE_SECURE` | По умолчанию `true`; требует HTTPS origin, в том числе при завершении TLS на reverse proxy. Для локального HTTP нужно явно указать `false`; с HTTPS это запрещено. |
| `ADMIN_SESSION_TTL` | `1h`, диапазон 1 минута — 24 часа; срок не продлевается запросами. |
| `ADMIN_DATABASE_TIMEOUT` | `5s`, общий бюджет проверки БД/миграций/импорта перед запуском. |
| `ADMIN_SCORING_URL` | Необязательный базовый URL МС1 для просмотра фактически скомпилированного каталога. |
| `ADMIN_SCORING_TIMEOUT` | `2s`, бюджет запроса метаданных; меньше общего административного deadline. |
| `ADMIN_REQUEST_TIMEOUT` | `30s`, deadline контекста HTTP-запроса и операций БД, включая подготовку релиза. |
| `HTTP_WRITE_TIMEOUT` | `45s`, должен превышать `ADMIN_REQUEST_TIMEOUT`; также ограничивает чтение запроса. Для МС1/МС2 значения по умолчанию остаются прежними. |

Пул использует максимум 5 соединений, 2 простаивающих. Заголовки ограничены 32 KiB. Пароли, connection strings, service/session/CSRF токены не журналируются; ошибки возвращают технические коды без исходных сообщений БД. У сервиса нет встроенных пользовательских паролей или сервисных секретов. Тестовые значения из тестов не предназначены для запуска.

Для генерации хеша используйте bcrypt с cost 10–14 и вводом пароля вне аргументов командной строки/истории оболочки. Пароль — не более 72 байт UTF-8 (ограничение bcrypt). Используется уже имеющийся `golang.org/x/crypto/bcrypt`; новая внешняя зависимость для авторизации не добавлена. API библиотеки: [официальная документация bcrypt](https://pkg.go.dev/golang.org/x/crypto/bcrypt).

## Браузерный доступ

| Маршрут | Запрос / результат |
|---|---|
| `GET /healthz` | Проверка работающего процесса без авторизации. |
| `POST /api/admin/v1/auth/login` | JSON с ровно двумя строками `username`, `password`; нужен точный заголовок `Origin`. Успех: 200, две cookie, `username`, `expires_at`, `csrf_token`. |
| `GET /api/admin/v1/auth/session` | Проверка cookie и срока в БД; 200 с пользователем, сроком и CSRF-токеном для восстановления страницы. |
| `POST /api/admin/v1/auth/logout` | Cookie, точный `Origin` и `X-CSRF-Token`. Успех: удаление сессии из БД и cookie, 204. |

Неавторизованный запрос получает 401, ошибка Origin/CSRF — 403, недоступность хранилища сессий — 503. Неверные имя и пароль имеют один ответ `INVALID_CREDENTIALS`. Вход принимает только `application/json`, до 4096 байт, отклоняет null, дубли, неизвестные/неверно названные ключи. На один процесс допускается 10 попыток входа в минуту суммарно, включая успешные: превышение — 429 с `Retry-After: 60`. Ограничитель не доверяет IP-заголовкам и сбрасывается при перезапуске; для MVP с одной учётной записью это общий лимит.

Cookie `credit_admin_session` и `credit_admin_csrf` содержат независимые случайные 256-битные значения, имеют `HttpOnly`, `SameSite=Strict`, `Path=/`, срок и настраиваемый `Secure`; Domain не задаётся. Сырые значения не записываются в БД. Session hash дополнительно связан с именем и хешем пароля: смена этих настроек с перезапуском отвергает прежние cookie. Сессии сохраняются при обычном перезапуске с неизменными credentials.

В PostgreSQL хранится максимум 10 сессий на пользователя. Каждый успешный вход транзакционно удаляет истёкшие записи и вытесняет наиболее старые при превышении лимита. Конкурентные входы сериализуются по пользователю. Проверка срока выполняется каждым запросом; истёкшая запись не авторизует даже до физической очистки. Выход удаляет запись; при ошибке БД сервер не подтверждает выход и не скрывает ошибку очисткой cookie.

Изменяющие запросы интерфейса требуют одновременно сессию, точный публичный `Origin` и заголовок `X-CSRF-Token`, совпадающий с nonce сессии. Cookie CSRF также HttpOnly: интерфейс получает nonce через JSON входа/проверки сессии и передаёт заголовком. Дубли cookies и заголовков защиты отклоняются. Сервисный токен не заменяет браузерную сессию. Ответы авторизации и защищённых маршрутов имеют `Cache-Control: no-store`.

Пароль, его хеш и сервисный токен никогда не возвращаются. Session cookie и CSRF nonce передаются только как необходимые данные успешной аутентификации. Сервис не включает CORS и не доверяет `X-Forwarded-*` для определения origin: публичный адрес задаётся настройкой.

## Доступ МС2

Клиент `clients.NewAdminWithToken` передаёт `Authorization: Bearer <ADMIN_EVENTS_TOKEN>` только при отправке административных событий. Проверка выполняется отдельным `Access.Service`; cookies браузера для неё недостаточно. Секреты сравниваются через сравнение хешей с постоянным временем. Повторы и редиректы HTTP-клиент самостоятельно не выполняет; это сохраняет прежние правила очереди МС2.

`config.LoadBank` принимает `ADMIN_EVENTS_TOKEN` и передаёт его через сборку МС2 в клиент. Пустая настройка сохраняет совместимость с прежним учебным получателем уведомлений; для доставки в новую админку токен необходим. Без него новая админка отвергнет доставку, а МС2 сохранит событие как недоставленное по прежним правилам. Неверный непустой формат токена блокирует запуск МС2.

Рабочий приём `POST /api/v1/credit-events`, сохранение до ACK, повторы и административное чтение описаны в [руководстве событий](26_credit_events.md). Сервер не подтверждает несохранённые события.

## Проверка

Изолированные HTTP-тесты проверяют вход/выход/срок, cookie, CSRF, Origin, разные credentials, поведение при перезапуске/смене пароля, отказы БД, лимит конкурентных входов, отсутствие исходных секретов в ошибках и запрет редиректа с токеном. PostgreSQL-тест под тегом `integration` проверяет реальные сессии, ограничение при конкурентных входах, истечение, удаление и откат вытеснения при неудачной вставке. Тестовая БД создаётся только в изолированном Docker-окружении по правилам [проверки схемы](22_admin_database.md).
