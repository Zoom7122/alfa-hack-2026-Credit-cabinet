# Предварительный расчёт и сравнение моделей

Административная симуляция использует те же `scoring.PrepareApplication`, `WithSupplierFacts`, `WithStatements`, DSL-движок и преобразование результата, что рабочая оценка. Она не вызывает поставщиков, МС2, оптимизатор или доставку событий, не сохраняет результат в БД и не изменяет действующую модель МС1. Применение модели в основном процессе требует подготовки комплекта и пересборки.

Маршруты защищены браузерной сессией, `Origin` и `X-CSRF-Token` по [правилам доступа](24_admin_access.md). Полный контракт — [административный OpenAPI](../contracts/admin.openapi.json).

## Самостоятельный набор

| Поле | Значение |
|---|---|
| `evaluation_date` | Обязательная календарная дата `YYYY-MM-DD`, используется как UTC-дата. Системные часы не участвуют в расчёте. |
| `application` | Именованный `DecisionRequest` по действующему контракту МС1. Допускается неполнота бизнес-данных для проверки `NEED_INFO`; технически неверные значения отклоняются. |
| `statements` | Именованный `StatementsResponse` для ЮЛ либо null. Неполные формы дают диагностику общей подготовки; поля произвольных кодов вместо структур не принимаются. Для ИП отчётность не используется. |
| `facts_date` | Дата дополнительных фактов либо null. При наличии должна быть `YYYY-MM-DD`, не позже оценки. При null возраст фактов неизвестен. |
| `additional_facts` | Объект именованных чисел/boolean/null либо null. Ключи задаются выбранной моделью. Пропуск и null означают неизвестность, `0`/`false` остаются известными значениями. |

Все пять ключей набора должны присутствовать. JSON проверяет UTF-8, глубину, дубли, имена и размер; весь административный запрос ограничен 4 MiB + 32 KiB, блок дополнительных фактов — 1 MiB. Неполные данные и некорректные типы различаются. Числа дополнительных фактов читаются теми же ограниченными декодерами, что сгенерированные DTO: соблюдаются int64/float64, числовые домены и точность целых. Разбор симуляции не расширяет лимит протокола поставщика.

Готовые полные наборы из исходных фикстур:

- [ИП v2](../testdata/simulation/ip-v2.json);
- [ЮЛ v2](../testdata/simulation/le-v2.json).

Из сообщения МС2 восстановить полный набор нельзя: оно не содержит всю заявку, отчётность и дополнительные входные значения.

## Один расчёт

`POST /api/admin/v1/simulations`:

```json
{
  "model": {"kind":"PUBLISHED","id":"ip-v2","revision":null},
  "sample": {"evaluation_date":"2026-10-23","application":{},"statements":null,"facts_date":null,"additional_facts":{}}
}
```

В примере `application` нужно заменить полным объектом из готового набора; пустой объект не имеет обязательной транспортной оболочки. Поле `sample` целиком можно взять из файла выше. Для черновика ссылка имеет вид `{"kind":"REVISION","id":"<draft UUID>","revision":3}`. Используется именно эта неизменяемая ревизия, даже если текущий черновик уже изменён.

Модель выбирается ссылкой `model`. Значение `application.model_version` не выбирает движок симуляции: один и тот же исходный запрос можно сравнивать на разных версиях. Ответ содержит фактически использованные `model_version`, SHA определения и дату оценки.

Модель обязана проходить общий валидатор. Некорректный черновик можно хранить, но его симуляция возвращает 422 `MODEL_VALIDATION_FAILED` с полным результатом проверки. Тип заёмщика модели должен соответствовать заявке.

Порядок сохраняет приоритеты рабочего МС1: подтверждённые стопы по заявке, дополнительные факты/стопы, затем отчётность ЮЛ и полный расчёт. Неиспользуемые при раннем стопе зависимые данные не влияют на решение.

## Диагностика

Ответ включает:

- `route`, `score`, причины и точный список недостающих полей;
- параметры модели: источник, единицу, ожидаемый тип, исходное и эффективное значение после проверки домена;
- критерии: значение/ответ, баллы/максимум, выбранный `case_id`, специальный случай, неизвестность, пропуск и причину рассмотрения;
- проверки качества с трёхзначным статусом `TRUE`, `FALSE`, `UNKNOWN`;
- стопы и правила рассмотрения: статус условия, прохождение обязательных проверок, подтверждение и фактическое применение с учётом приоритетов.

Значение содержит `known`, тип, числовое представление, JSON `value` и `exact_value`. Последнее сохраняет текст точного целого/рационального значения; клиенту следует использовать его для чисел за пределами безопасной точности JavaScript.

Критерии дополнительно объясняются изолированно, в том числе при неполной заявке или раннем стопе. `contributes_to_score` явно указывает, включён ли критерий в окончательный балл. При `score=null` предварительные значения отдельных критериев не являются итоговой оценкой. `SELECT_OFFER` означает готовность модели к подбору предложения; выдача и `APPROVED` в симуляции отсутствуют.

## Сравнение

`POST /api/admin/v1/simulations/compare` принимает `left`, `right` (такие же точные ссылки) и один общий `sample`.

Обе версии используют одну заявку, отчётность, дополнительные значения и дату. Блок дополнительных фактов может содержать объединение имён двух выбранных моделей; каждая версия читает свои именованные поля по своему типу/домену. Если данные несовместимы с контрактом одной из моделей, возвращается ошибка входных данных. Внешние данные отдельно для каждой версии не запрашиваются.

Ответ содержит оба результата, сравнение определений, изменение маршрута/класса, разницу округлённых и исходных итогов, а также изменившиеся критерии. Разница баллов отдельного критерия вычисляется только когда он участвовал в обоих итогах; в остальных случаях `points_delta=null`. Отсутствие итогового балла также не превращается в нулевой итог.

## Проверка

Симуляция сверяется с рабочим скомпилированным оценщиком по всем 18 исходным шаблонам решений, включая ИП/ЮЛ, неполноту, стопы и рассмотрение. Отдельная генерация и реальная компиляция будущих моделей с именованными nullable DTO подтверждает равенство их результатов предварительному расчёту. Проверяются точные int64 выше `2^53`, boolean/null, явная дата, границы классов, неизменность входа и изоляция диагностических копий движка.

PostgreSQL HTTP-проверка фиксирует число черновиков/ревизий/версий/релизов/записей истории/событий до и после симуляции и сравнения. Числа не меняются; скомпилированный каталог МС1 остаётся прежним.
