# Входные данные и скоринг МС1 — версия 2

Вопросы, диапазоны и веса утверждённой модели v2 приведены в таблицах ниже. У ИП: 31 анкетный пункт (21 балльный), 13 дополнительных показателей. У ЮЛ: 27 пунктов (20 балльных), 18 дополнительных показателей.

**Анкета А: максимум 750. Дополнительные расчёты МС1: максимум 250. Общий максимум: 1000.** Контрольные пункты дают 0; наличие строки в анкете не отменяет её стопа или требования документов. Все формулы, сравнения диапазонов и начисление баллов реализуются в Go. Excel — справочник для человека; сервис его не читает. Готовые баллы/коэффициенты от А/Б не принимаются.

## 1. JSON и Go-типы

Полный источник типов — [contract.go](../contracts/contract.go); соответствующая схема REST — [openapi.json](../contracts/openapi.json). Поля экспортируемые, с однозначными json-тегами. Вместо универсальной карты полей используются конкретные структуры.

```go
type ScoringInput struct {
    IP          *IpScoring          `json:"ip"`
    LegalEntity *LegalEntityScoring `json:"legal_entity"`
}
// Фрагмент; полный перечень полей — в contract.go.
type IpScoring struct {
    OwnerAge             *int          `json:"owner_age"`
    MaritalStatus        *MaritalStatus `json:"marital_status"`
    CurrentDPDDays       *int          `json:"current_dpd_days"`
    NetMonthlyIncomeRUB  *int64        `json:"net_monthly_income_rub"`
}
type LegalEntityScoring struct {
    BusinessAgeMonths        *int `json:"business_age_months"`
    ManagerExperienceYears   *int `json:"manager_experience_years"`
    ReportVerificationLevel  *int `json:"report_verification_level"`
}
```

В DecisionRequest.scoring передаётся ровно одна ветка по borrower.type: SOLE_PROPRIETOR → ip; LEGAL_ENTITY → legal_entity. Другая ветка отсутствует/null. Обе заполнены или тип не совпал → 422; отсутствующая нужная ветка → NEED_INFO. Пропущенное поле и null означают неизвестное значение; указатель после json.Unmarshal будет nil. Явные 0/false сохраняются. Обязательность по бизнесу проверяет Go-код; схема допускает неполную анкету для результата NEED_INFO.

Все анкетные числа неотрицательны, целочисленны; report_verification_level ∈ {0,1,2,3}. Для категорий используются только коды ниже. Неизвестный код/отрицательный счётчик → 422; неверный JSON-тип поля → 400, а не кредитный отказ. Анкета не содержит выбранной категории баллов вместо исходного возраста, дней просрочки и т. п. У категориальных вопросов код обозначает ответ, а баллы выбирает код МС1.

| monthly_history | 12 последовательных завершённых месяцев; MonthCash содержит поступления, переменные/постоянные выплаты, налоги, поддерживающие вложения, необходимые выплаты владельцу и обслуживание действующих долгов. |

| evidence | Подтверждённые поступления и абсолютное необъяснённое расхождение за 12 месяцев; largest_buyer_group_receipts_rub — поступления крупнейшей связанной группы покупателей. |
| ip_economic_data | Только ИП: previous_comparable_receipts_rub за предыдущие сопоставимые 12 месяцев. |
| scoring | Исходные ответы и подтверждённые факты по одной анкете ниже. |

История денежных операций нужна обоим типам: у ЮЛ для CFADS/платёжеспособности, но не добавляет новые баллы сверх 18 утверждённых коэффициентов. Баланс/ОФР её не заменяют. Для ИП учитываются необходимые личные изъятия и обслуживаемые из общего потока личные долги; для ЮЛ — обязательства организации, без автоматического добавления личных долгов владельца. Новые кредиты, вклады владельца и собственные переводы не являются операционной выручкой. Все выплаты передаются положительными суммами; обслуживание долга не дублируется в операционных выплатах.

У ИП обязательны все поля своей анкеты, кроме military_status и условного location_stability_months: последний нужен только при VERIFIED_PHYSICAL. У ЮЛ все поля своей анкеты обязательны. Неизвестный проверяемый факт → null → NEED_INFO, а не предположение «риска нет». Для ЮЛ evidence.largest_buyer_group_receipts_rub и ip_economic_data не требуются и баллов не дают; остальные исходные подтверждения денежного потока сохраняются для проверки достоверности.

## 4. Отчётность Б: только ЮЛ

После ранних стопов МС1 получает через REST два последних завершённых годовых комплекта (последний конец периода не старше 365 дней): AnnualReport{year, period_end, balance, profit_and_loss}; StatementsResponse содержит borrower_id и annual_reports. ИП Б не вызывает. При дате оценки 23.10.2026 нужны 2024 и 2025 годы с period_end 31 декабря. Текущие факты — до 45 дней, годовая отчётность проверяется по своему году, без требования давности 45 дней.

Balance — именованный BalanceShit, ОФР (отчёт о прибылях и убытках) — именованный ProfitAndLoss, без map строк. Каждое денежное поле *int64, единица каждой формы *StatementUnit: RUB или THOUSAND_RUB. МС1 нормализует перед вычислениями. В названиях полей Б нет суффикса RUB, поскольку исходная единица формы может быть тысячами рублей.

Основные строки классических документов представлены отдельными полями; примечания/подробные расшифровки для MVP не нужны. Коды и названия сверены с [примером форм в ресурсе ФНС](https://bo.nalog.gov.ru/download/bfo/pdf/50809587). Б приводит данные своих источников к этому контракту. Это компактное представление для расчёта, а не формат сдачи бухгалтерской отчётности.

## 5. Дополнительная оценка: общие обозначения

За последние 12 месяцев: R=сумма операционных поступлений; CFADS месяца=поступления−переменные−постоянные выплаты−налоги−поддерживающие вложения−необходимые выплаты владельцу; F=сумма CFADS; D=обслуживание существующих долгов за эти месяцы; C=свободные деньги после собственного участия; Q=среднемесячные постоянные выплаты+необходимые выплаты владельцу+действующий долг. Долговые платежи при CFADS ещё не вычитаются. Среднее балансовой строки=(значение на конец предыдущего года+на конец последнего)/2. Если год не указан, берётся последний полный год.

Коэффициенты и начисления ниже рассчитывает МС1, они не являются входом А/Б. Проценты в таблицах — отображение долей; в Go и EconomicCriterion.value хранятся доли (0.10=10%), дни/разы/счётчики — натуральные числа. Автономия и финансовая независимость — один и тот же критерий, второго начисления нет. Показатели рентабельности/ликвидности — отдельные утверждённые коэффициенты, даже если используют общие исходные строки.

Дополнительно: если R=0, CFADS при неотрицательных выплатах не может быть положительным; при достоверном полном потоке применяется стоп F≤0. Если последняя выручка ЮЛ=0, нулевой знаменатель в маржах/DSO даёт соответствующему критерию 0 и ручное основание; приоритет стопа/D сохраняется. Средние активы≤0 → 0 для ROA и оборачиваемости, ручное основание. Отрицательный чистый долг возможен и оценивается первым диапазоном LE_E07. Факт отрицательного собственного капитала сам по себе не добавляет нового стопа: это особое правило показателя/ручной маршрут из справочника.

Для обоих типов сохраняются проверки достоверности поступлений: confirmed_receipts/R <80% либо unexplained_difference/R >10% → NEED_INFO, а не плохой балл вместо подтверждения. Для ИП эти же отношения имеют свои единственные строки IP_E10/IP_E11. Для ЮЛ они проверяют данные для платёжеспособности, но не добавляют баллы. При 5%<расхождение/R≤10% — ручное основание. Месяцев с CFADS>0 меньше 8 — ручное основание для обоих типов; у ИП IP_E05 даёт баллы, у ЮЛ отдельного балльного критерия за месяцы нет. Это сохраняет прежние проверки качества денежного потока.

## 6. Единичные стопы и приоритет решения

**Одного подтверждённого стопа достаточно для REJECTED независимо от любых 750/250 баллов.** Это раннее правило, а не начисление «0 баллов» с последующим возможным одобрением.

| Код причины | Подтверждённое условие |
|---|---|
| INACTIVE_BORROWER | scoring.<ветка>.active=false. |
| BANKRUPT | bankrupt=true. |
| MATERIAL_FORGERY | material_forgery=true. |
| CREDIT_PROHIBITED | credit_prohibited=true. |
| LIQUIDATED_OR_EXCLUDED | Только ЮЛ: liquidated_or_excluded=true. |
| CURRENT_DPD_30_PLUS | current_dpd_days≥30. |
| WORST_REPAID_DPD_90_PLUS | worst_repaid_dpd_days_24m≥90. |
| NONPOSITIVE_VERIFIED_CFADS | F≤0 при полном актуальном подтверждённом денежном наборе. |

Известный стоп из А обрабатывается до ожидания всех остальных полей и до Б. Переданные риск-факты и дни просрочки означают проверенные А значения; если факт ещё не установлен, А передаёт null, а не предположение. Денежный стоп требует 12 полных корректных месяцев, актуальных фактов, documents_complete/free_cash_source_verified=true и подтверждённой полноты обязательств; проверки поступлений должны пройти. Иначе отрицательный/нулевой предполагаемый поток не является подтверждённым стопом: запросить данные. При очевидном стопе score=null допустим и обязателен в эталонах, МС2/МС3 не вызываются. Отсутствующее подтверждение риска не считается ни true, ни false.

Порядок после технического разбора: **известный стоп → нехватка данных → полный балл → класс D → ручное основание → подбор → банк**. У ЮЛ документные/денежные проверки не позволяют обойти реальный стоп или нехватку данных. Невалидный JSON/тип — техническая ошибка, не REJECTED.

Ручные основания из анкет/доп. таблиц действуют только после устранения нехватки данных и проверки D. Также сохраняются: просроченные налоги >10% F; нестандартная цель; недостаточный свободный остаток C<C_min; отсутствие непокрытой подтверждённой потребности; отсутствие допустимых условий подбора. Класс C сам по себе достаточен для ручного маршрута. Поступления крупнейшего покупателя и подтверждённые поступления не превышают R; долг=0 при положительном графике требует уточнения. Месяцы истории/графика уникальны, последовательны и соответствуют дате оценки.

## 7. Итог и представление результата

S_анкеты=сумма анкетных баллов (0…750); S_экономики=сумма дополнительных (0…250); raw_total=S_анкеты+S_экономики. Все веса уже выражены в конечных баллах: повторного умножения на 0.75/0.25 нет. Экономические дробные баллы не округляются по критериям или блоку. Total=округление raw_total до целого один раз, половина вверх. Только Total определяет класс; отдельного порога анкеты нет.

| Итог | Класс | Дальше при отсутствии более приоритетного основания |
|---|---|---|
| 800…1000 | A | Подбор и проверка банка. |
| 650…799 | B | Подбор и проверка банка. |
| 550…649 | C | UNDER_REVIEW/BORROWER через ручной маршрут МС2. |
| 0…549 | D | REJECTED без МС2. |

ScoreResult содержит отдельно questionnaire (points, max_points=750, criteria с ответом/баллами), economics (points, max_points=250, criteria со значением/баллами), raw_total, total и grade. ID вопросов/показателей стабильны и совпадают с таблицами. В questionnaire.criteria включаются все 31/27 пунктов, контрольные — с max_points=points=0; непереданный необязательный воинский статус отображается OTHER_OR_UNKNOWN. answer — воспроизводимое строковое представление исходного значения/кода или результата контрольной проверки, не вход для начисления баллов. Model=ip-v2 либо legal-v2.

Если обязательных данных нет, итоговый score=null; нормировать неполный набор на 1000 нельзя. Анкетные ответы используются в одном месте, коэффициенты — в своём блоке. Ни класс, ни баллы не зависят от выбранной суммы/срока/ставки. Подтверждённые стопы и платёжеспособность баллами не компенсируются.

## 8. Что реализовать в Go

Чистые функции проверки, вычисления показателей, switch/if по анкетным значениям и диапазонам; суммирование и определение класса. Значения весов/порогов этой версии закрепить в коде модели с табличными тестами. Не загружать скоринг из Excel/JSON во время работы; config/policy.json сохраняет общую банковскую экономику, а не таблицу ответов. Не принимать готовые коэффициенты/баллы из А или Б.

Проверки должны покрыть каждый вариант ответа, обе стороны каждой границы, 750/250/1000, нули/null, единичные стопы на иначе сильной анкете, каждый особый знаменатель, фактическую полноту Б и отсутствие побочных действий у отказа/нехватки данных. Начисление по отражённому в ответе answer не заменяет switch по типизированному исходному полю.
