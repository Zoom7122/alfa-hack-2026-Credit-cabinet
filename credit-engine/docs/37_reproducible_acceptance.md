# Воспроизводимая комплексная приёмка Linux/Docker

Из каталога `credit-engine/` на Linux с Docker Engine и Docker Compose:

```sh
sh scripts/verify.sh
```

Скрипт собирает рабочий образ, запускает весь модуль и выполняет проверки. Он возвращает ненулевой код при первой ошибке. На Linux-хосте Go, PostgreSQL, Node.js и браузер устанавливать не требуется; они работают в контейнерах. Для первого запуска нужны доступ к реестрам образов, Go-модулям и npm. Версии инструментов заданы в compose.acceptance.yaml и scripts/verify.sh.

## Состав стенда

`compose.acceptance.yaml` — самостоятельный тестовый стек с отдельным именем проекта:

- PostgreSQL 16 с учебными учётными данными и временным хранилищем;
- однократные миграции, административный МС3, МС2 и МС1 из рабочего Dockerfile;
- подменные HTTP-поставщики Б и новых фактов; тестовый прокси перед настоящим МС2 сохраняет исходящие запросы МС1;
- Go-контейнер для race/integration, vet, сборки и modelgen;
- Node.js и Chromium/Playwright для сценариев API и настольного интерфейса;
- отдельные МС1/МС2 для проверки модели, реально пересобранной из скачанного релиза.

МС1/МС2/МС3, их клиенты, БД, скоринг и подбор работают без подмены. Подменяются только внешние поставщики данных. Стенд не подключается к общей БД и внешним сервисам проекта. Тестовые логин, пароль и сервисный токен публичны и предназначены исключительно для этого изолированного стенда.

Админка доступна с хоста по `http://localhost:18084`, пока стенд работает. МС1, МС2 и PostgreSQL не публикуют порты на хост. По умолчанию все контейнеры, сеть и временная БД этого прогона удаляются при завершении, включая ошибочное.

## Что проверяется

1. `go test -race -tags=integration -count=1 -shuffle=on -json ./...`: все пакеты и PostgreSQL-интеграции, без кеширования результатов. Затем `go vet ./...`, сборка всех шести CLI/сервисов и `modelgen validate/check`.
2. 27 JavaScript-проверок точных чисел и операций редактора.
3. 11 базовых браузерных сценариев до появления сообщений.
4. Все 17 историй из testdata/scenarios.json (18 решений), затем 7 банковских примеров по настоящему HTTP. Сравниваются полные ответы, исходящие DTO, вызовы Б/поставщика, состояние банка и сохранённые события МС3. Идентичный повтор проверяет отсутствие второй выдачи и дубля события.
5. Остановка МС3: выдача с PENDING; после восстановления идентичные повторы доставляют прежнее событие, сохраняя одну выдачу. На восстановление соединений отведено до 20 секунд; состояние банка проверяется после каждой попытки.
6. 10 браузерных сценариев редактора, симуляции, конфликтов, блокировки неверных весов, подготовки/скачивания ZIP и просмотра событий.
7. Сквозной расчёт базовой модели МС1 → МС2 → МС3 с проверкой идемпотентности.
8. Проверенный архив релиза применяется к новой копии модуля внутри `.work`, запускаются modelgen check и сборка МС1. Новый бинарный файл принимает сгенерированные boolean/number-поля от агрегатора, его расчёт сравнивается с симуляцией админки. Повтор обращается к поставщику с идентичным телом.
9. Запуск `/admin-password` из рабочего образа и итоговая проверка полноты артефактов.

Каждая независимая история запускается со своим начальным снимком и новым МС2. Два шага UC-06 используют один экземпляр. Идентификаторы заявок получают суффикс прогона, чтобы события разных историй не конфликтовали. Сравнение следует действующим правилам эталонов: клиентские status/message, коды причин и числовые результаты проверяются точно с финансовыми допусками; свободные тексты reasons.message/detail должны быть непустыми, пустой эталонный список полей причины допускает уточняющие поля. Поля причин сравниваются без учёта порядка. Ответ на идентичный повтор сравнивается строго. Сетевой стенд фиксирует дату оценки МС1 на 2026-10-23. Для `occurred_at` проверяются корректный UTC и сохранение при повторах; численное значение фиксированных часов эталона проверяют Go-тесты с подменой часов.

## Артефакты и управление

Результаты находятся в `.work/re-audit/<имя-прогона>/`: `verification.json`, JSONL Go-тестов и сетевых сценариев, вывод vet/build/modelgen, отчёты браузера, скачанный архив, пересобранный бинарный файл, снимки интерфейса и логи контейнеров. Скрипт печатает путь при завершении. Кеши инструментов также находятся в `.work`.

```sh
# Другой доступный порт хоста; внутри стенда порт остаётся 18084.
CREDIT_ENGINE_TEST_PORT=18085 sh scripts/verify.sh

# Сохранить стенд для осмотра после прогона.
KEEP_TEST_STACK=1 CREDIT_ENGINE_TEST_LABEL=ce-inspect sh scripts/verify.sh
# Завершить именно сохранённый проект, включая его временную БД.
export CREDIT_ENGINE_TEST_LABEL=ce-inspect
export CREDIT_ENGINE_TEST_SOURCE="$PWD"
export CREDIT_ENGINE_TEST_WORK_HOST="$PWD/.work/re-audit/ce-inspect"
export CREDIT_ENGINE_TEST_OUTPUT=/workspace/credit-engine/.work/re-audit/ce-inspect
docker compose -p ce-inspect -f compose.acceptance.yaml --profile checks down --remove-orphans --volumes
```

Имя прогона должно быть новым: повторное использование каталога с готовой копией для пересборки отклоняется. При работе Docker CLI внутри контейнера `CREDIT_ENGINE_TEST_SOURCE` должен указывать абсолютный путь исходного каталога, видимый Docker daemon; на обычном Linux-хосте он вычисляется автоматически. При нестандартной настройке соединения с Docker передайте соответствующее окружение Docker CLI.

Это проверка согласованности модуля на синтетических данных, а не проверка доступности реальных А/Б/поставщика, общего стека или производительности. Windows-сборка и мобильный интерфейс в область приёмки не входят.
