# Подключение Credit Engine

Credit Engine содержит один Go-модуль и три отдельных HTTP-сервиса на Gin: МС1 оценивает заявки, МС2 проверяет сделки и хранит учебное состояние банка, МС3 предоставляет админку моделей и сохраняет события. Форматы определены в [OpenAPI](../contracts/openapi.json) и [Go DTO](../contracts/contract.go); запуск и настройки — в [README](../README.md).

`DecisionRequest.financial_statements` — необязательный снимок бухотчётности из проверенных документов конкретной заявки. Он разрешён только для ЮЛ, `borrower_id` должен совпадать с `borrower.id`. Если снимок передан, МС1 использует его вместо запроса поставщику Б, сохраняя проверки периодов, единиц, полноты и арифметики. Без поля поставщик Б вызывается как прежде. Неполный снимок даёт `NEED_INFO`, пропущенные строки не становятся нулями.

| Участник / владелец | Что предоставить или адаптировать |
|---|---|
| Отправитель А | POST DecisionRequest в МС1. Передавать scoring.ip либо scoring.legal_entity по типу заёмщика, 12 месяцев операций и 36 месяцев долгов, минимум суммы и максимум срока. Коэффициенты и баллы рассчитывает МС1. |
| Поставщик Б | GET двух годовых комплектов баланса/ОФР. Именованные BalanceShit/ProfitAndLoss, единицы у каждой формы; поле для каждой строки по контракту, без map кодов. Только для ЮЛ. |
| Административный МС3 Credit Engine | Принимает POST /api/v1/credit-events с дедупликацией event_id и сохраняет его в PostgreSQL до ACK. Показывает выдачу, ручную заявку или банковскую проблему; решений сотрудника в MVP нет. |
| Владелец общего API/кабинета | Принять четыре результата МС1 и отдельное основание рассмотрения. Кредитные ставки во всех REST-контрактах — проценты: 1 = 1%, 24 = 24%, 23.75 = 23,75%; допустимо 0..100, до двух знаков после точки. Нормативы и коэффициенты остаются долями единицы. |
| Владелец общего конвейера | APPROVED нашего MVP уже означает учебную выдачу и изменение банка. Подписание не должно повторно учитывать кредит. |
| Владелец корневого Compose/Makefile | Подключить три HTTP-сервиса и отдельный запуск миграций из образа Credit Engine, PostgreSQL для МС3 и адреса внешних зависимостей. Образец — compose.credit-engine.yaml; изменение общего стека выполняется его владельцем. |
| Владелец общей БД | МС1/МС2 не используют БД. Админка сохраняет модели, релизы, сессии и события в собственной схеме PostgreSQL; миграции описаны в docs/22_admin_database.md. Сохранение других результатов общей системой выполняется её адаптером. |

## Контейнерный образ и общий стек

В каталоге `credit-engine/` находятся `Dockerfile` и `.dockerignore`. Контекст сборки — именно этот каталог. Из корня репозитория образ собирается так:

```sh
docker build -t credit-engine:local ./credit-engine
```

Образ содержит шесть исполняемых файлов: три HTTP-сервиса и CLI `/admin-migrate`, `/admin-password`, `/modelgen`. Каждый контейнер запускает один выбранный процесс:

| Настройка | МС1 | МС2 | МС3 |
|---|---|---|---|
| Образ | `credit-engine:local` | `credit-engine:local` | `credit-engine:local` |
| Compose `build.context` относительно корневого Compose | `./credit-engine` | `./credit-engine` | `./credit-engine` |
| `entrypoint` | `["/scoring-service"]` (по умолчанию) | `["/bank-state-service"]` | `["/admin-service"]` |
| HTTP-порт по умолчанию | `8082` | `8083` | `8084` |
| Подключения | `BANK_URL`, `STATEMENTS_URL`, `FACTS_URL` для моделей с новыми фактами | `ADMIN_URL`, `ADMIN_EVENTS_TOKEN` | `ADMIN_DATABASE_URL`, доступ администратора, `ADMIN_EVENTS_TOKEN`, `ADMIN_SCORING_URL` |

Миграции выполняются до старта МС3 отдельным контейнером с `entrypoint: ["/admin-migrate"]` и `command: ["up"]`. PostgreSQL и секреты для рабочего стека настраиваются по [руководству поставки](33_container_delivery.md).

Имена сервисов в URL должны совпадать с DNS-именами в общей Docker-сети. Если Compose переопределяет имя МС2 или его HTTP-порт, измените `BANK_URL`. Все прочие переменные приведены в README. Публикация портов на хост нужна только для обращений с хоста; межсервисные вызовы используют внутренние порты. Объявление `EXPOSE` само порты не публикует. В Compose выбирайте МС2 через `entrypoint`, а не через `command`.

Сборка создаёт статические Go-бинарные файлы; финальный образ на `distroless/static-debian12:nonroot` содержит их и конфигурацию, работает без прав root. Рабочий каталог `/app`; политика и три стартовых снимка доступны в `/app/config`. Для внешних конфигураций подключайте читаемые непривилегированным пользователем JSON-файлы через bind mount только для чтения и задавайте `POLICY_FILE`/`BANK_STATE_FILE`. Политика МС1 и МС2 должна совпадать. Конфигурация читается при запуске; после изменения нужен перезапуск.

Контейнеры завершаются по `SIGTERM` с ожиданием HTTP-запросов до 5 секунд. Для проверки процесса используйте `GET /healthz` из внешнего HTTP-клиента: в образе нет shell, `curl` или `wget`. Эта проверка не подтверждает готовность Б/МС3. Обязательные URL должны быть заданы даже при отдельном запуске контейнера.

МС1/МС2 не требуют PostgreSQL, Kafka или тома для изменяемого состояния. Состояние, идемпотентность и события МС2 сохраняются только до перезапуска; для этого MVP запускайте один экземпляр МС2. Пример отдельных `docker run` приведён в README. МС3 входит в Credit Engine; Б и агрегатор фактов предоставляются внешними участниками. Изолированный тестовый стек с подменными поставщиками описан в [воспроизводимой приёмке](37_reproducible_acceptance.md).

## А → МС1: оценка заявки

Статические версии моделей и один запрос МС1 к агрегатору дополнительных фактов реализованы по [контракту поставщика и правилам версий](09_scoring_facts_contract.md). Подключение новой модели требует генерации DTO, проверок и пересборки. Базовая v2 не запрашивает новые факты; значения новых фактов от А не требуются.

`POST /api/v1/decisions` возвращает HTTP 200 и один из статусов `NEED_INFO`, `REJECTED`, `UNDER_REVIEW`, `APPROVED`. Для рассмотрения указан `review_reason=BORROWER` либо `BANK`. Только `APPROVED` подтверждает условия (`terms_confirmed=true`) и означает уже учтённую учебную выдачу. При банковском рассмотрении предложенные условия показаны как неподтверждённые; при ручном рассмотрении заёмщика `terms=null`.

Вход содержит исходные факты и именованную анкету по [описанию скоринга](02_inputs_and_scoring.md). Для ИП нужны также денежная история, подтверждения, потребность и данные для дополнительных показателей; одного возраста/семейного положения недостаточно. Пропуск или null не заменяется нулём/false. Долговой график содержит 36 явных месяцев, включая нули после погашения; весь текущий долг может превышать сумму платежей в этом горизонте.

Кредитные ставки передаются числами в процентах: `1` = 1%, `23.75` = 23,75%, `100` = 100%. Диапазон 0..100 включительно, не более двух знаков после точки. Остальные коэффициенты сохраняют доли единицы. Деньги запроса — целые рубли; даты — `YYYY-MM-DD`, месяцы — `YYYY-MM`.

Технические ошибки возвращаются отдельно в формате `Problem` (`application/problem+json`): 400 — JSON/тип или обязательное техническое поле; 422 — недопустимое значение; 409 — конфликт операции/политики; 502/504 — ошибка/тайм-аут обязательной зависимости; 500 — внутренняя ошибка. Чужой идентификатор в ответе зависимости даёт 502. Эти ошибки не являются кредитным отказом или рассмотрением.

## МС1 → Б: годовая отчётность ЮЛ

После ранних стопов МС1 вызывает `GET /api/v1/borrowers/{borrower_id}/statements?years=2024,2025`. Годы в примере соответствуют дате оценки в 2026 году; фактически всегда нужны два последних завершённых года. `borrower_id` передаётся отдельным закодированным сегментом пути. ИП этот маршрут не вызывает.

Успешный ответ — HTTP 200 и `StatementsResponse` с тем же `borrower_id`, двумя `AnnualReport`, датами окончания периода и именованными `BalanceShit`/`ProfitAndLoss`. Каждая форма указывает `RUB` либо `THOUSAND_RUB`. Значения строк — целые числа в указанной единице; готовые коэффициенты не заменяют строки отчётности.

HTTP 404 означает отсутствие форм и приводит к `NEED_INFO`. Корректный, но неполный или противоречивый комплект также требует уточнения данных. Неверный JSON/тип, неизвестная единица, чужой `borrower_id`, недоступность и неожиданный HTTP-статус — техническая ошибка, а не отсутствие форм. Дополнительные JSON-поля игнорируются.

## МС2 → МС3: административные события

МС2 отправляет `POST /api/v1/credit-events` с `Authorization: Bearer <ADMIN_EVENTS_TOKEN>`. Один сервисный секрет настраивается в МС2 и МС3; браузерная сессия не заменяет его. Приёмник реализован административным сервисом, сохраняет сообщение в PostgreSQL до ACK. Подробности доступа, чтения и фильтров — в [руководстве событий](26_credit_events.md) и [административном OpenAPI](../contracts/admin.openapi.json).

| `kind` | Что показать администратору |
|---|---|
| `LOAN_ISSUED` | Учтённую выдачу, заёмщика, скоринг и условия; заполнены `loan_id` и `terms`. |
| `BORROWER_REVIEW` | Ручную заявку, исходные пожелания, скоринг и причины; `terms`/`loan_id` равны null, банковская проекция отсутствует. |
| `BANK_REVIEW` | Выбранную сделку и проблемные банковские проверки в `problems`; выдачи нет, `loan_id=null`. |

`event_id = application_id + ":" + kind`, `occurred_at` — время UTC в RFC3339. МС3 должен принимать повторы `event_id` идемпотентно. Доставка подтверждается только HTTP 202 с `accepted=true` и тем же идентификатором:

```json
{
  "event_id": "application-001:LOAN_ISSUED",
  "accepted": true
}
```

Другой статус, неверный ответ или сетевая ошибка оставляют `notification_status=PENDING` в ответе МС2. Уже учтённая выдача сохраняется. Идентичный повтор исходной операции МС2 повторяет только недоставленное событие с прежними ID и временем. После подтверждения повторной отправки нет. Фоновой доставки и отдельного маршрута повторов в MVP нет.

## Адреса, время и повторные обращения

Порты по умолчанию: МС1 `:8082`, МС2 `:8083`, МС3 `:8084`. В МС1 задаются `BANK_URL`, `STATEMENTS_URL` и при необходимости `FACTS_URL`, в МС2 — `ADMIN_URL`, в МС3 — `ADMIN_SCORING_URL`; к базовым URL добавляются пути из контрактов. Можно использовать префикс пути, но не query, fragment или учётные данные. В контейнерах адрес зависимости должен разрешаться из контейнера вызывающего сервиса; `localhost` обозначает его собственное сетевое окружение.

Тайм-аут МС1 → МС2 по умолчанию 4 секунды, Б, поставщика фактов и доставки МС2 → МС3 — 2 секунды; WriteTimeout МС1/МС2 — 15 секунд. У МС3 бюджет административной операции 30 секунд и WriteTimeout 45 секунд; запрос метаданных МС1 — 2 секунды. Если значения изменяются, сохраняйте время для последовательных обращений и доставки. `GET /healthz` проверяет работающий процесс; доступность внешних участников он не проверяет.

До первого вызова МС2 данные заявки `NEED_INFO` можно дополнить под прежним `application_id`. МС2 сравнивает декодированные DTO: одинаковая операция возвращает прежний результат без новой выдачи, изменение содержимого/маршрута либо несовпадение `policy_id` даёт 409. Для новой оценки после терминального результата нужен новый ID. После потери ответа повтор безопасен при неизменных исходных данных и политике; отдельного кеша МС1 нет.

Состояние банка, результаты операций и события находятся в памяти МС2. Перезапуск сбрасывает их к выбранному стартовому снимку. Финансовое состояние можно наблюдать через `GET /api/v1/bank/state` в МС2; в публичный ответ МС1 банковские агрегаты, нормативы и SelectionAudit не включаются.

Прежняя карта A–E, альтернативные офферы, pgqueue, ML, подпись и WebSocket не входят в обязательную реализацию наших сервисов. Общий жизненный цикл заявки может быть шире, но не переопределяет наши бизнес-правила.

Пометка EXTERNAL-B в сгенерированном контракте описывает внешний сервис отчётности. Уведомления МС2 теперь обслуживает входящий в Credit Engine административный МС3; его административные операции описаны отдельным contracts/admin.openapi.json. PostgreSQL нужна МС3, а МС1/МС2 сохраняют прежние зависимости. Брокер сообщений не требуется.

## Админка, поставка и работающие версии

Новая модель встраивается в МС1 при сборке. GET /api/v1/models возвращает фактические версии и SHA-256 каталога; административный GET /api/admin/v1/runtime/models запрашивает эти сведения через ADMIN_SCORING_URL. Подготовленный релиз не считается запущенным. Контракт метаданных — contracts/scoring_metadata.openapi.json.

Полная поставка, параметры сети/секретов и отдельные миграции описаны в docs/33_container_delivery.md, процедура согласованного обновления контрактов и возврата — в docs/36_release_and_integration.md. Общие Compose/Makefile/CI/БД по-прежнему настраивают владельцы стека.
