# Подключение Credit Engine

Credit Engine содержит один Go-модуль и два отдельных HTTP-сервиса на Gin: МС1 оценивает заявки, МС2 проверяет сделки и хранит учебное состояние банка. Форматы определены в [OpenAPI](../contracts/openapi.json) и [Go DTO](../contracts/contract.go); запуск и настройки — в [README](../README.md).

| Участник / владелец | Что предоставить или адаптировать |
|---|---|
| Отправитель А | POST DecisionRequest в МС1. Передавать scoring.ip либо scoring.legal_entity по типу заёмщика, 12 месяцев операций и 36 месяцев долгов, минимум суммы и максимум срока. Коэффициенты и баллы рассчитывает МС1. |
| Поставщик Б | GET двух годовых комплектов баланса/ОФР. Именованные BalanceShit/ProfitAndLoss, единицы у каждой формы; поле для каждой строки по контракту, без map кодов. Только для ЮЛ. |
| Владелец МС3 | POST /api/v1/credit-events с дедупликацией event_id. Показывать выдачу, ручную заявку или банковскую проблему. После уведомления история заканчивается. |
| Владелец общего API/кабинета | Принять четыре результата МС1 и отдельное основание рассмотрения. Кредитные ставки во всех REST-контрактах — проценты: 1 = 1%, 24 = 24%, 23.75 = 23,75%; допустимо 0..100, до двух знаков после точки. Нормативы и коэффициенты остаются долями единицы. |
| Владелец общего конвейера | APPROVED нашего MVP уже означает учебную выдачу и изменение банка. Подписание не должно повторно учитывать кредит. |
| Владелец корневого Compose/Makefile | При необходимости добавить сборку и адреса двух наших сервисов; изменение выполняется в своей зоне ответственности. |
| Владелец общей БД | При желании сохранять результаты через свой адаптер. Нашим сервисам БД не требуется. |

## А → МС1: оценка заявки

`POST /api/v1/decisions` возвращает HTTP 200 и один из статусов `NEED_INFO`, `REJECTED`, `UNDER_REVIEW`, `APPROVED`. Для рассмотрения указан `review_reason=BORROWER` либо `BANK`. Только `APPROVED` подтверждает условия (`terms_confirmed=true`) и означает уже учтённую учебную выдачу. При банковском рассмотрении предложенные условия показаны как неподтверждённые; при ручном рассмотрении заёмщика `terms=null`.

Вход содержит исходные факты и именованную анкету по [описанию скоринга](02_inputs_and_scoring.md). Для ИП нужны также денежная история, подтверждения, потребность и данные для дополнительных показателей; одного возраста/семейного положения недостаточно. Пропуск или null не заменяется нулём/false. Долговой график содержит 36 явных месяцев, включая нули после погашения; весь текущий долг может превышать сумму платежей в этом горизонте.

Кредитные ставки передаются числами в процентах: `1` = 1%, `23.75` = 23,75%, `100` = 100%. Диапазон 0..100 включительно, не более двух знаков после точки. Остальные коэффициенты сохраняют доли единицы. Деньги запроса — целые рубли; даты — `YYYY-MM-DD`, месяцы — `YYYY-MM`.

Технические ошибки возвращаются отдельно в формате `Problem` (`application/problem+json`): 400 — JSON/тип или обязательное техническое поле; 422 — недопустимое значение; 409 — конфликт операции/политики; 502/504 — ошибка/тайм-аут обязательной зависимости; 500 — внутренняя ошибка. Чужой идентификатор в ответе зависимости даёт 502. Эти ошибки не являются кредитным отказом или рассмотрением.

## МС1 → Б: годовая отчётность ЮЛ

После ранних стопов МС1 вызывает `GET /api/v1/borrowers/{borrower_id}/statements?years=2024,2025`. Годы в примере соответствуют дате оценки в 2026 году; фактически всегда нужны два последних завершённых года. `borrower_id` передаётся отдельным закодированным сегментом пути. ИП этот маршрут не вызывает.

Успешный ответ — HTTP 200 и `StatementsResponse` с тем же `borrower_id`, двумя `AnnualReport`, датами окончания периода и именованными `BalanceShit`/`ProfitAndLoss`. Каждая форма указывает `RUB` либо `THOUSAND_RUB`. Значения строк — целые числа в указанной единице; готовые коэффициенты не заменяют строки отчётности.

HTTP 404 означает отсутствие форм и приводит к `NEED_INFO`. Корректный, но неполный или противоречивый комплект также требует уточнения данных. Неверный JSON/тип, неизвестная единица, чужой `borrower_id`, недоступность и неожиданный HTTP-статус — техническая ошибка, а не отсутствие форм. Дополнительные JSON-поля игнорируются.

## МС2 → МС3: административные события

МС2 отправляет `POST /api/v1/credit-events`. Только МС2 обращается в МС3.

| `kind` | Что показать администратору |
|---|---|
| `LOAN_ISSUED` | Учтённую выдачу, заёмщика, скоринг и условия; заполнены `loan_id` и `terms`. |
| `BORROWER_REVIEW` | Ручную заявку, исходные пожелания, скоринг и причины; `terms`/`loan_id` равны null, банковская проекция отсутствует. |
| `BANK_REVIEW` | Выбранную сделку и проблемные банковские проверки в `problems`; выдачи нет, `loan_id=null`. |

`event_id = application_id + ":" + kind`, `occurred_at` — время UTC в RFC3339. МС3 должен принимать повторы `event_id` идемпотентно. Доставка подтверждается только HTTP 202 с `accepted=true` и тем же идентификатором:

```json
{
  "event_id": "application-001:LOAN_ISSUED",
  "accepted": true
}
```

Другой статус, неверный ответ или сетевая ошибка оставляют `notification_status=PENDING` в ответе МС2. Уже учтённая выдача сохраняется. Идентичный повтор исходной операции МС2 повторяет только недоставленное событие с прежними ID и временем. После подтверждения повторной отправки нет. Фоновой доставки и отдельного маршрута повторов в MVP нет.

## Адреса, время и повторные обращения

Порты по умолчанию: МС1 `:8082`, МС2 `:8083`. В МС1 задаются `BANK_URL` и `STATEMENTS_URL`, в МС2 — `ADMIN_URL`; к базовым URL добавляются пути из контракта. Можно использовать префикс пути, но не query, fragment или учётные данные. В контейнерах адрес зависимости должен разрешаться из контейнера вызывающего сервиса; `localhost` обозначает его собственное сетевое окружение.

Тайм-аут МС1 → МС2 по умолчанию 4 секунды, Б и МС3 — 2 секунды; серверный WriteTimeout — 15 секунд. Если эти значения изменяются, необходимо сохранить время для последовательных обращений и доставки МС2 → МС3. `GET /healthz` проверяет работающий процесс; доступность внешних участников он не проверяет.

До первого вызова МС2 данные заявки `NEED_INFO` можно дополнить под прежним `application_id`. МС2 сравнивает декодированные DTO: одинаковая операция возвращает прежний результат без новой выдачи, изменение содержимого/маршрута либо несовпадение `policy_id` даёт 409. Для новой оценки после терминального результата нужен новый ID. После потери ответа повтор безопасен при неизменных исходных данных и политике; отдельного кеша МС1 нет.

Состояние банка, результаты операций и события находятся в памяти МС2. Перезапуск сбрасывает их к выбранному стартовому снимку. Финансовое состояние можно наблюдать через `GET /api/v1/bank/state` в МС2; в публичный ответ МС1 банковские агрегаты, нормативы и SelectionAudit не включаются.

Прежняя карта A–E, альтернативные офферы, pgqueue, ML, подпись и WebSocket не входят в обязательную реализацию наших сервисов. Общий жизненный цикл заявки может быть шире, но не переопределяет наши бизнес-правила.

Пути Б и МС3 отмечены в OpenAPI как EXTERNAL-B/EXTERNAL-MS3. Credit Engine предоставляет клиенты этих участников; их серверные реализации в поставку не входят. Общие Compose/OpenAPI/БД настраиваются владельцами соответствующих компонентов. БД и брокер сообщений для запуска МС1/МС2 не требуются.
