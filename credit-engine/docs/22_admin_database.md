# PostgreSQL административного сервиса

Админка использует собственную схему `credit_engine_admin` в PostgreSQL 16. Состояние банка и реестр выдач МС2 остаются отдельными. Общие миграции соседних компонентов не входят в этот комплект.

## Структура

| Таблица | Назначение |
|---|---|
| `model_drafts` | Черновик, текущая ревизия, автор/время и отметка удаления |
| `model_revisions` | Сохранённые определения, SHA256, автор, основание и состав изменения |
| `model_versions` | Неизменяемые опубликованные определения и метаданные схем поставщика |
| `prepared_releases` | Канонический манифест, ZIP, SHA256, описание изменений и базовый релиз |
| `change_history` | История действий с автором, временем, основанием и деталями |
| `credit_events` | События МС2, идентификаторы, время, исходное содержимое и SHA256 |
| `admin_sessions` | Хеши токена/CSRF, учётная запись и срок действия сессии |
| `goose_db_version` | Учёт только административных миграций |

Определения хранятся как канонические JSON-документы в текстовом поле с проверкой JSON-объекта. Это сохраняет пробелы и исходную запись числовых литералов, необходимые для воспроизводимого SHA256. JSONB используется для структурированных сведений об изменениях, где лексическая запись не определяет контрольную сумму. Добавление поля скоринга не создаёт новую колонку.

Текущая ревизия связана с сохранённой составным отложенным внешним ключом. Черновик и первая ревизия создаются одной транзакцией; обновление указателя и добавление ревизии также завершаются вместе. Неверный указатель не может быть зафиксирован. SQL не проверяет максимум баллов черновика: промежуточное определение с ошибками можно сохранить; выпуск проверяется общей библиотекой модели/релиза.

Ревизии, опубликованные модели, подготовленные релизы, история и принятые события защищены от UPDATE/DELETE триггерами. Черновики имеют отдельную отметку удаления; история сохраняется. Сессии допускают удаление при выходе/истечении срока. Контрольные суммы содержимого вычисляет и проверяет Go-код; расширения PostgreSQL не требуются.

## Миграции

SQL находится в `migrations/admin/` и встроен в `admin-migrate`. Используются pgx v5.11.0 и Goose v3.29.0, согласованные с зависимостями общего модуля `db`.

```sh
export ADMIN_DATABASE_URL='postgres://admin:example-password@postgres:5432/credit_admin?sslmode=disable'
go run ./cmd/admin-migrate status
go run ./cmd/admin-migrate up
go run ./cmd/admin-migrate status
```

`ADMIN_DATABASE_URL` задаётся отдельно для административного подключения. Инструмент не читает корневой `.env` и не изменяет конфигурацию общего стека. Открытие пула не соединяется с БД и не выполняет DDL; команда явно проверяет доступность перед миграцией. Применение не выполняется при обычном открытии хранилища.

- `up` создаёт собственную схему и применяет только встроенные административные миграции; повтор не меняет применённую схему.
- `status` показывает состояние. До первого применения он возвращает pending без создания схемы.
- `down` откатывает последнюю административную миграцию и удаляет её данные. Схема и собственная таблица учёта сохраняются для корректной записи отката; соседние таблицы не затрагиваются.
- `-timeout 30s` задаёт общий лимит подключения/операции; должен быть положительным.

Создание схемы сериализовано транзакционной advisory-блокировкой. Goose использует отдельную session-блокировку этого компонента и имя `credit_engine_admin.goose_db_version`. Все прикладные объекты квалифицированы схемой; глобальное состояние Goose не используется. Общий `public.goose_db_version` не участвует.

Обычно используются до пяти открытых и двух простаивающих соединений; подключение ограничено пятью секундами, если URL не задаёт положительный тайм-аут. Нормальные сообщения ошибок не содержат URL/пароль или SQL-параметры. Исходная причина остаётся доступной контролируемому коду через errors.Is/As.

## Проверка на изолированной БД

Интеграционные тесты включаются тегом `integration`. Они требуют `CREDIT_ENGINE_TEST_ISOLATED=1` и отдельную исходную БД с именем `credit_engine_admin_test` в `CREDIT_ENGINE_TEST_DSN`. Внутри выделенного тестового экземпляра для каждого теста создаётся отдельная временная БД; тестовая роль должна иметь право CREATE DATABASE. Эти БД удаляются после прогона. Таблицы-маркеры соседних компонентов создаются только внутри временных БД.

```text
go test -tags=integration -count=1 -v ./internal/adminstore
go test -race -tags=integration -count=1 -v ./internal/adminstore
```

Команды можно повторять на том же выделенном тестовом экземпляре; рабочая БД приложения не используется.

Проверяются конкурентные первые `up`, повторное применение, откат/повтор, приватная таблица Goose, состав схемы, хранение определения без изменения числовых токенов, новая ревизия/параметр без DDL, недопустимый указатель ревизии, неизменяемые записи, срок сессии и сохранение false/null события. Содержимое таблиц-маркеров и общего учёта миграций сравнивается после операций.

Документация зависимостей: [Goose Provider](https://pkg.go.dev/github.com/pressly/goose/v3@v3.29.0#Provider), [pgx database/sql](https://pkg.go.dev/github.com/jackc/pgx/v5@v5.11.0/stdlib).
