# Общая библиотека скоринга

Расчёт разделён на чистое исполнение модели в [internal/rules](../internal/rules/engine.go) и подготовку существующих финансовых данных в [internal/scoring](../internal/scoring/preparation.go). Библиотека не запрашивает А/Б/поставщика, не работает с БД, не обращается к банку и не отправляет события. Дата оценки задаётся явно. Это общая основа для статической модели МС1 и предварительной оценки черновика админкой.

## Порядок вызова

| Вызов | Результат |
|---|---|
| `rules.Compile(definition, catalog)` | Проверка модели и собственная глубокая копия определения; неизменяемый исполнитель для конкурентных оценок. |
| `scoring.PrepareApplication(request, date)` | Техническая проверка А, именованные факты, точные агрегаты, расчёты ИП и CashFlow. Нулевая дата отклоняется. |
| `engine.Stops(prepared.Input)` | Подтверждённые стопы до внешних вызовов. Отсутствие стопа ещё не означает достаточность данных. |
| `scoring.WithStatements(prepared, response)` | Проверка/нормализация полученных форм Б и расчёты ЮЛ. Переданный prepared не изменяется. |
| `scoring.WithAdditionalFacts(prepared, values)` | Новая копия с числовыми/логическими фактами поставщика, без возможности затереть источники А/Б. Проверка wire-оболочки относится к REST-адаптеру. |
| `scoring.EvaluatePrepared(engine, prepared)` | Внутренний результат маршрута, баллов, причин и проверок, плюс CashFlow для последующего подбора. |
| `engine.EvaluateCriterion(id, input)` | Изолированное объяснение одного критерия с тем же исполнением случаев и нужными зависимостями; возвращает недостающие поля, не кредитное решение. |
| `engine.Classify(raw)` | Единственное итоговое округление и класс по встроенной шкале; используется и полным Evaluate. |

Работающий процесс передаёт встроенное определение; JSON модели используется инструментами/редактором. При предварительной оценке админка компилирует проверенный черновик и передаёт самостоятельные тестовые данные с явной датой. Выбор/загрузка версии, HTTP и окончательное оформление REST-ответа остаются внешним слоем.

## Факты и точность

rules.Value различает неизвестность, 0, false и строку категории. Значение неизменяемо; big.Int/big.Rat копируются при создании и чтении. Числа сохраняют представление источника из доверенного каталога: int64, точные агрегаты/отношения и прежние float64. Несоответствие типа или числового представления — явная ошибка, NaN/Inf не допускаются. Значение вне домена модели требует уточнения данных.

Input.Values привязан к model.Source, а не редактируемому ID параметра. Переименование ID не теряет связь с полем. Origins и FieldOrigins сохраняют исходные пути родительских блоков, месяцев и годовых форм, чтобы внутренние имена нормализованных строк не попадали в запрос недостающих сведений.

Расчёты всех 13/18 коэффициентов выделены в [metrics.go](../internal/scoring/metrics.go). Прежний расчёт v2 и новая библиотека используют одни финансовые функции. Расчёт значения отделён от выбора баллов и причин. При неизвестном/неопределённом коэффициенте возвращается неизвестное значение; подтверждённый нулевой знаменатель обрабатывается special_cases модели без деления.

Повторная WithStatements заменяет факты и производные показатели отчётности целиком. Неполный новый комплект не сохраняет значения из предыдущего; исходная подготовка вызывающей стороны остаётся неизменной.

## Условия, баллы и маршруты

Условия используют трёхзначную логику. ALL с FALSE и ANY с TRUE дают известный результат даже при других неизвестных операндах; NOT неизвестного остаётся неизвестным. KNOWN/UNKNOWN проверяют состояние, а не истинность значения. Числовые пороги интерпретируются в представлении сравниваемого источника; двоичные коэффициенты не переводятся в другую финансовую семантику.

Порядок результата:

1. Подтверждённые ранние стопы А.
2. Подтверждённые зависимые стопы, включая денежный.
3. Обязательность, применимость и проверки достаточности; при нехватке данных — NEED_INFO.
4. Критерии по порядку: особый случай либо один обычный диапазон; двойного начисления нет.
5. Суммы блоков, единственное half-up округление итога и класс.
6. D возвращает отказ со своей причиной, C добавляет причину в начало ручных оснований; остальные ручные основания ведут на рассмотрение, при их отсутствии — SELECT_OFFER.

Ручные причины до критериев и after_criterion сохраняют заданный порядок. ZERO сохраняет неизвестный критерий с нулём и unknown_text, SKIP не добавляет его, NEED_INFO запрашивает необходимые исходные данные. Эти политики не отменяют required и data_checks. Результаты критериев содержат выбранный case, признак специального случая, неизвестность, типизированное значение, ответ, баллы и максимум. Проверки возвращают passed/skipped, трёхзначный статус, исходные поля и пояснение.

Это внутреннее представление. Рабочий конвейер МС1 использует compiled-каталог и `ToAssessment`; прежнее числовое представление v2 сохранено, логический результат передаётся как JSON boolean. Порядок внешних обращений и выбор версии описаны в [процессе МС1](19_versioned_pipeline.md).
