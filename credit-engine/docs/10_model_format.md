# Формат определения скоринговой модели

Версия формата — `format_version=1`. Типы определены в [пакете model](../internal/model/definition.go), строгий разбор — в [codec.go](../internal/model/codec.go). [Каталог моделей](../models/README.md) содержит отдельные примеры формата. Это данные редактора и генератора: работающий МС1 использует скомпилированную модель и не читает эти JSON-файлы при оценке.

Формат сохраняет идентификаторы, баллы и порядок критериев v2 и позволяет описывать новые числовые/boolean-параметры. Полные определения ip-v2/legal-v2 и доверенные привязки описаны в [каталоге исходных моделей](12_v2_model_sources.md); примеры с суффиксом format-fragment остаются неполными фрагментами.

## 1. ModelDefinition

| Поле | Содержание |
|---|---|
| format_version | Версия синтаксиса документа, сейчас 1. |
| id | Семейство модели, например ip или legal. |
| version | Полный неизменяемый wire-идентификатор версии, например ip-v2. Это model_version протокола и score.model результата. |
| borrower_type | SOLE_PROPRIETOR либо LEGAL_ENTITY. |
| title / description | Название и необязательное пояснение для администратора/документации. |
| facts_schema_version | Схема поставщика для именованных новых полей; нужна при использовании поставщика. Не заменяет version/policy_id/идентификатор релиза. |
| parameters | Упорядоченные объявления параметров и привязки к источникам. |
| criteria | Упорядоченные балльные и контрольные критерии. |
| data_checks | Проверки достаточности/достоверности бизнес-данных, включая известный false у контрольного подтверждения. |
| stops | Подтверждённые основания отказа. |
| manual_reviews | Основания рассмотрения заёмщика. |
| classes | Полная шкала целого итогового балла с классами A–D. |

Все поля без `omitempty` в Go-описании обязательны в JSON. Пустые списки передаются `[]`, не `null`. enabled и required всегда указываются явно. Необязательные поля можно опустить; неизвестное значение бизнес-факта не представляется удалением служебных полей определения.

Массивы сохраняют порядок: он нужен для прежних критериев/пояснений v2 и детерминированной генерации. Идентификаторы параметров и критериев — разные пространства имён. Критерии ИП/ЮЛ сохраняют IP_Qxx/IP_Exx и LE_Qxx/LE_Exx.

## 2. Источники и параметры

Parameter содержит id, enabled, title, description, source, json_name, необязательное go_name, type, unit, домен, required, required_when и depends_on.

| source.kind | source.path |
|---|---|
| APPLICATION | Существующая именованная привязка исходного поля А, например scoring.ip.owner_age. |
| STATEMENTS | Именованная строка нормализованных годовых форм Б; current/previous обозначают последний/предыдущий завершённый год, значения денег нормализованы в RUB. |
| COMPUTED | Идентификатор существующего расчёта Go, например IP_E07. Произвольные формулы запрещены. |
| SUPPLIER | JSON-имя нового поля additional_facts, совпадающее с json_name. |

Привязки APPLICATION/STATEMENTS/COMPUTED сверяются с доверенным каталогом кода, включая тип, единицу и зависимости. Добавить новую расчётную функцию одним JSON-описанием нельзя. Binding описывает этот доверенный каталог; он не является редактируемой формулой. У depends_on в Parameter — ID параметров модели, у Binding — привязки Source, необходимые существующему расчёту. Их согласованность проверяется при подготовке модели.

json_name фиксирует имя источника/генерируемого поля; go_name позволяет явно задать экспортируемое имя нового Go-поля. Коллизии, недопустимые имена и расхождение с доверенным существующим полем блокируются валидатором. Смена источника не создаёт новое поле в базе админки.

Типы: NUMBER, BOOLEAN и STRING. STRING сохраняет существующие категориальные входы; новые SUPPLIER-параметры допускают только NUMBER/BOOLEAN. Домены:

- NUMBER: number.integer, необязательные lower/upper с value и inclusive. Отсутствующая граница означает отсутствие ограничения модели с этой стороны; сохраняются пределы представления источника. NaN/Infinity недопустимы.
- BOOLEAN: известные true/false; неизвестность хранится отдельно, не как false.
- STRING: явный string_values для существующей категории; строки не становятся Go-кодом или формулой.

Единицы перечислены явно: RUB, RATIO, PERCENT, COUNT, MONTHS, YEARS, DAYS, BOOLEAN, CATEGORY, DATE. Они не выполняют неявное преобразование. Кредитные ставки REST сохраняют прежнее представление процентов; единицы банковской политики не меняются редактором.

required=true требует известного факта, если required_when отсутствует либо условие истинно. required_when сужает область обязательности: например, location_stability_months нужен для VERIFIED_PHYSICAL. Если неизвестно само условие обязательности, нельзя считать его ложным и молча пропустить данные. Необходимые для решения зависимости должны быть получены/указаны как недостающие. Отключённый параметр не может оставаться зависимостью активного критерия/правила/расчёта.

Числовые границы и Literal.number хранят исходный десятичный токен json.Number: 9007199254740993 не округляется до 9007199254740992 при чтении/сохранении. В JSON это числа; строки с числом недопустимы. Один токен ограничен 256 байтами, модуль десятичной экспоненты — 512; требуется конечное представление float64. Само сравнение определяется доверенным Binding.NumericKind: INT64 для целых входов, INTEGER для точных агрегатов, RATIONAL для прежних проверок денежных отношений, FLOAT64 для балльных коэффициентов и нормализованных форм Б. У FLOAT64 пороги получают прежнее бинарное представление; целые и точные отношения сравниваются без промежуточного округления. Новый целый SUPPLIER использует int64, дробный — float64. Редактор должен сохранять числовые токены без потерь и в браузере.

## 3. Условия и значения

Literal содержит ровно один из number, boolean, string. Ненулевой указатель означает известное значение, в том числе `{"number":0}` и `{"boolean":false}`. Пустой Literal и несколько вариантов одновременно некорректны; неизвестность не является литералом для сравнения.

Condition использует только следующие формы:

| op | Поля |
|---|---|
| ALWAYS / NEVER | Без операндов. |
| ALL / ANY | Непустой список conditions. |
| NOT | Ровно один элемент conditions. |
| KNOWN / UNKNOWN | parameter. |
| EQ / NE / LT / LE / GT / GE | parameter и ровно один из value/other_parameter. |
| IN / NOT_IN | parameter и непустой список values одного подходящего типа. |

Сравнения порядка предназначены числам; проверка принадлежности поддерживает известные значения объявленного типа. Сравнение с другим параметром не вводит арифметику. Нужные коэффициенты уже должны существовать в доверенном каталоге расчётов.

Оценка условий трёхзначная: TRUE, FALSE, UNKNOWN. ALL с известным FALSE даёт FALSE, ANY с известным TRUE даёт TRUE; в остальных случаях неизвестные операнды сохраняют UNKNOWN. NOT UNKNOWN остаётся UNKNOWN. KNOWN/UNKNOWN проверяют присутствие известного значения и всегда дают определённый boolean. Условие стопа подтверждено только при TRUE.

У числовых диапазонов открытость границ выражается LT/LE/GT/GE и ALL. Для дискретных integer-доменов учитываются достижимые целые значения, а для непрерывных — все интервалы и сами границы. Перекрывающиеся варианты и пропуски не исправляются перестановкой правил.

## 4. Критерии и начисление

Criterion задаёт id, enabled, title/description, block, value_parameter, answer, max_points, applies_when, unknown_action, special_cases, cases.

Rule может указывать requires_checks — идентификаторы проверок data_checks, подтверждающих основание. Например, денежный стоп требует подтверждённой истории, свежести, качества поступлений и полноты долгов. Для такого стопа недостаточно одного CFADS≤0. Редактирование проверки меняет и подтверждённость зависимого стопа. Проверки оцениваются перед стопами, но ответ NEED_INFO формируется после подтверждённых стопов. Неприменимая проверка считается пройденной; неизвестная/неудовлетворённая применимая проверка не подтверждает стоп. Истинный денежный стоп с неподтверждёнными зависимостями сохраняет свой путь monthly_history среди недостающих данных.

after_criterion допустим только у manual_reviews: основание добавляется после указанного критерия. Так сохраняются NONPOSITIVE_EQUITY после LE_E05 и основания прибыли/убытков после LE_E12; обычные ручные основания идут до критериев. Валидатор проверяет существование/включённость зависимых проверок и критерия. Порядок special-case причин сохраняется по criteria, класс C добавляется первым; класс D возвращает только свою причину.

- QUESTIONNAIRE соответствует прежнему questionnaire и максимуму 750; ADDITIONAL — economics и максимуму 250. max_points — целое число, сохраняющее тип действующих DTO. Баллы случаев ADDITIONAL могут быть дробными, например 3,75; QUESTIONNAIRE сохраняет целые баллы прежнего представления.
- value_parameter указывает исходное/расчётное значение для результата и шкалы. Контрольный вопрос может не иметь единственного значения и использовать постоянный ответ.
- answer сохраняет текстовые ответы анкеты. template содержит только обычный текст и `${parameter_id}`; поддерживаются условные cases с when/template для составного ответа IP_Q18. unknown_text задаёт явное представление допустимой неизвестности, например OTHER_OR_UNKNOWN у IP_Q31. Произвольный шаблонный язык/вызовы функций не исполняются.
- applies_when определяет применимость критерия. Неопределённость нужных условий не превращается в FALSE. Неприменимый критерий не начисляет баллов; веса других критериев не нормируются.
- unknown_action явно задаёт реакцию на неизвестный необходимый для начисления факт: NEED_INFO, ZERO или SKIP. ZERO сохраняет критерий с нулём/неизвестным значением; SKIP не добавляет его в результат начисления. Объявленные максимумы модели автоматически не меняются. Эти политики не отменяют обязательность параметров/проверки достаточности.

Сначала проверяются special_cases. Они выражают существующие особые случаи, например нулевой знаменатель: points=0, result.mode=NULL и review_reason=SPECIAL_IP_E07. При подтверждённом специальном случае обычная шкала не используется; неизвестность, мешающая однозначному выбору, не подменяется отрицательным ответом. Если специального случая нет, ровно один обычный case назначает points. Не складываются несколько вариантов одного критерия.

ScoreCase содержит id, when, points и необязательные description, result, review_reason. result отсутствует — сохранить рассчитанное значение; mode=NULL — вернуть неизвестное/неопределённое значение; mode=VALUE с одним Literal — явно вернуть известную специальную константу. Это представление результата, не новая формула. ReviewReason содержит code/message/fields и добавляет основание рассмотрения в порядке критериев. Контрольные max_points=0 сохраняются в описании и результате v2.

Максимумы активных критериев проверяются отдельно: ровно 750/250/1000 для каждого типа заёмщика. Промежуточный черновик может иметь другой итог, но не выпускается. По ходу начисления дробные баллы не округляются; итог округляется half-up один раз, затем выбирается класс. Отдельный порог анкеты не вводится.

## 5. Достаточность, стопы, рассмотрение и классы

DataCheck содержит id/enabled/title, необязательный applies_when, satisfied_when, fields и message. Если применимая проверка не подтверждена, сведения недостаточны: NEED_INFO с путями исходных полей. Это позволяет выразить, что известное bureau_received=false не равно отсутствующему полю, но всё равно не подтверждает полноту. Подтверждённые стопы остаются приоритетнее неполноты.

Rule для stops/manual_reviews содержит id/enabled/title, when и reason(code/message/fields). Стопы проверяются по доступным фактам на предусмотренных фазах процесса; неизвестный предикат не подтверждает стоп. Данные поставщика проверяются до Б, а правила, которым нужны формы/расчёты, — после появления соответствующих фактов. Правило не запускает HTTP-вызов или банковскую операцию самостоятельно.

ClassBand задаёт grade и включительные min_total/max_total, при необходимости reason. Шкала должна полностью и без пересечений покрывать 0..1000 и содержать A–D. Существующие границы: D 0–549, C 550–649, B 650–799, A 800–1000. Границы редактируются новой версией; маршруты D→отказ, C→рассмотрение, A/B→подбор при отсутствии более приоритетных оснований сохраняются. Модель не назначает банковское APPROVED самостоятельно.

Технический разбор/типы/ID и расчётные инварианты процесса не отменяются data_checks. В частности, редактор не позволяет выполнять банковский подбор без необходимых финансовых входов или изменять банковские нормативы. Изменения остаются в пределах [спецификации админки](08_admin_spec.md).

## 6. Кодек и границы проверки

Decode читает один JSON-объект размером не более 4 MiB и глубиной не более 64. Отклоняет дубли ключей, второй документ, неизвестные поля, пропуски обязательных служебных ключей, null вместо служебного scalar/object/array, неверные типы и неподдерживаемую format_version. FormatError содержит JSON Pointer path, code, message. Ошибки чтения сохраняются через wrapping.

Marshal сохраняет порядок, типы, значения/дроби и возвращает детерминированный JSON с завершающим переводом строки. Нормализация весов, перестановка критериев или замена неизвестности нулём не выполняются.

Кодек проверяет форму документа. Семантический валидатор отдельно проверяет каталоги/типы/имена, домены, формы условий, диапазоны/пропуски, ссылки/циклы/отключение, баллы/максимумы и классы. Поэтому документ с недостаточным количеством баллов можно прочитать и сохранить как черновик; такой документ нельзя подготовить к выпуску. Успешный Decode не означает готовность релиза.

Реализованный чистый валидатор, его адресные ошибки и ограничения точной проверки описаны в [проверке модели перед выпуском](11_model_validation.md). JSON-имена служебных полей проверяются с точным регистром: Enabled не является заменой enabled и не может перезаписать его второй формой ключа.
