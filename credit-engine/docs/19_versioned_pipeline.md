# Версии и дополнительные факты в процессе МС1

МС1 исполняет определения из сгенерированного Go-каталога. Модель не загружается из JSON, БД или админки во время оценки. Каталог проверяется и компилируется один раз при запуске процесса; его неизменяемые исполнители используются совместно. Новая версия требует генерации, сборки, тестов и развёртывания.

## Выбор версии

`POST /api/v1/decisions` принимает необязательное строковое `model_version` рядом с `application_id`. Отсутствующее поле сохраняет `ip-v2` для ИП и `legal-v2` для ЮЛ. Явная версия выбирается точно; перехода к «последней» нет.

| Вход | Результат |
|---|---|
| Поле отсутствует | Фиксированная legacy v2 |
| Поддерживаемая строка для этого типа заёмщика | Указанная compiled-модель |
| null, иной тип, повторяющийся ключ или неоднозначный регистр ключа версии | 400 INVALID_JSON |
| Пустая, неизвестная или чужая по типу заёмщика версия | 422 UNSUPPORTED_MODEL_VERSION, поле model_version |

После выбора `X-Scoring-Model-Version` содержит точную версию, в том числе при NEED_INFO, отказе с `score=null` и ошибке зависимости. При наличии результата `score.model` содержит ту же версию. Прежний JSON ответа v2 сохранён.

## Порядок выполнения

1. Проверить транспорт А, выбрать модель и подготовить доступные факты и денежные показатели с явной датой.
2. Выполнить доступные подтверждённые стопы. При отказе не вызывать поставщика, Б или МС2.
3. Если модель использует SUPPLIER, выполнить один [агрегированный запрос](09_scoring_facts_contract.md) с точными ID и версиями. Использовать именованный DTO этой модели и сохранить весь блок для расчёта.
4. Проверить стопы из полученных фактов до Б и до проверки полноты. Подтверждённый стоп сохраняет приоритет над неизвестным обязательным фактом.
5. Для ЮЛ получить два годовых комплекта Б; затем проверить полноту, вычислить критерии и класс. Неизвестный обязательный факт даёт NEED_INFO без банка. Известные 0/false сохраняются.
6. Продолжить прежний процесс: D → отказ; ручные основания → рассмотрение; иначе реальный подбор одной сделки → МС2. Только МС2 учитывает выдачу и отправляет уведомление МС3.

Недоступность или ошибочный ответ поставщика дают 502; тайм-аут — 504. Б, МС2 и уведомления после такой ошибки не вызываются. Исходный контекст передаётся поставщику; автоматических повторов и кеша МС1 нет.

Дата `facts_date` сохраняется в контексте как `prepared.supplier_facts_age_days`. Она не заменяет дату А/оценки и не вводит неявного порога свежести. При необходимости модель явно использует этот технический возраст в проверке. Новые финансовые формулы не добавляются.

## Запуск и повторы

Если хотя бы одна compiled-модель требует поставщика, запуск требует `FACTS_URL` и положительного `FACTS_TIMEOUT`. Сумма тайм-аутов поставщика, Б и МС2 должна быть меньше `HTTP_WRITE_TIMEOUT`. По умолчанию это 2 + 2 + 4 < 15 секунд. Если все модели обходятся без поставщика, клиент не создаётся и URL не требуется.

Повтор с прежними ID и явно указанной версией формирует тот же запрос поставщику. Поставщик гарантирует одинаковый ответ. Повторная выдача и дубли уведомления предотвращаются существующим реестром МС2; новый идентификатор или дата для обхода повторов не добавляются.

## Проверка совместимости

Обычная приёмка v2 выполняется через рабочий compiled-конвейер. Отдельный тест генератора компилирует полный пробный релиз с v2 и новыми именованными схемами и исполняет реальные Gin API МС1/МС2, расчёт, подбор, банковскую память и доставку уведомления. Только внешние зависимости/сеть подменены, реальные сервисы не запускаются. Проверяются порядок обращений, null/false, ранние стопы, ошибки и повтор.

В действующем каталоге сохранены утверждённые `ip-v2` и `legal-v2`. Пробные модели не публикуются; новое бизнес-определение включается явным комплектом релиза.
