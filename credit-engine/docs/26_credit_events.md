# Приём и просмотр событий МС2

Админка принимает существующий `POST /api/v1/credit-events`. Имена и смысл полей `AdminEvent` сохранены. Актуальные правила доступа и маршруты чтения описаны в [административном OpenAPI](../contracts/admin.openapi.json); исходные бизнес-события — в [интеграционном руководстве](05_integration.md).

## Доставка и фиксация

Отправитель передаёт `Authorization: Bearer <ADMIN_EVENTS_TOKEN>` и `Content-Type: application/json`. Нужен тот же сервисный секрет, который настроен в МС3. Cookie браузера и его CSRF-токен не авторизуют отправителя. Браузерный вход не нужен сервисному запросу.

Обработчик последовательно:

1. Проверяет сервисный доступ.
2. Проверяет JSON, именованный контракт и `event_id`.
3. Сохраняет событие либо находит ранее сохранённое идентичное.
4. Завершает транзакцию PostgreSQL.
5. Возвращает 202 с `accepted=true` и тем же `event_id`.

```json
{"event_id":"application-001:LOAN_ISSUED","accepted":true}
```

При ошибке вставки, чтения или commit успешный ACK не отправляется. У МС2 остаётся `PENDING`; уже выполненная учебная выдача не отменяется. Потеря ACK после commit безопасна: идентичный повтор подтверждается без новой записи. Повтор ID с другим содержимым возвращает 409 `EVENT_CONFLICT` и не меняет прежнее событие. Первая дата приёма также не изменяется.

Вставка использует уникальный ID и `ON CONFLICT DO NOTHING`, после чего отдельный запрос читает зафиксированного конкурентного победителя. Все сравнения происходят до commit, ответ — после него. Никаких UPDATE опубликованного события не выполняется; дополнительная защита неизменяемости действует в БД.

Содержимое сравнивается по SHA-256 канонического JSON именованного `AdminEvent`. Пробелы, порядок ключей и эквивалентное JSON-представление чисел не создают новый типизированный объект. Число, boolean и null различаются; `false` не становится нулём или отсутствующим значением. Стабильные ID, время и payload при повторах формирует сам МС2.

## Проверка контракта

Запрос ограничен 1 MiB. Отклоняются невалидный UTF-8, U+0000 (несовместим с проверяемым JSON PostgreSQL), повторные/неизвестные/неверно названные ключи, пропуск обязательного поля, null обязательного непоинтерного значения, неправильный тип и лишний JSON-документ. Nullable-поля должны присутствовать; для них null сохраняется явно. Проверка охватывает вложенные DTO и объединённое `value` экономического критерия: number, boolean или null.

`event_id = application_id + ":" + kind`, время — UTC RFC3339. Принимаются только `LOAN_ISSUED`, `BORROWER_REVIEW`, `BANK_REVIEW`, а также действующие типы заёмщика и классы A–D. Проверяются обязательные данные заёмщика/пожеланий, диапазон итогового балла и исходные ограничения условий/ставки. Ставка — проценты: 1 = 1%, максимум 100%, не более двух знаков. Это проверка сообщения, без повторного расчёта скоринга или банковской операции.

| Тип | Обязательная форма |
|---|---|
| `LOAN_ISSUED` | Непустой `loan_id`, выбранные `terms` и `selection`. |
| `BORROWER_REVIEW` | `loan_id`, `terms`, `selection` равны null, присутствуют причины. |
| `BANK_REVIEW` | `loan_id=null`, выбранные `terms`/`selection`, непустые банковские `problems`. |

Типизированный payload хранится целиком, вместе с SHA-256, временем события и первой датой приёма. Чтение повторно проверяет SHA и согласованность индексируемых полей с payload. PostgreSQL-метаданные времени имеют микросекундную точность, исходная строка времени остаётся в payload.

## Просмотр

Нужна административная браузерная сессия, описанная в [доступе к сервису](24_admin_access.md). Bearer МС2 не предоставляет доступа к чтению.

| Маршрут | Ответ |
|---|---|
| `GET /api/admin/v1/events` | Массив кратких записей без полного payload. |
| `GET /api/admin/v1/events/{event_id}` | `summary` с метаданными и полный `payload`. ID нужно кодировать как сегмент URL; поддерживаются непрозрачные ID с `/`, `+`, `%`, пробелами и другими допустимыми символами. |

Список сортируется по времени события по убыванию, затем по ID. Поддерживаются:

- `kind`, `borrower_type` — точные значения типов;
- `application_id`, `borrower_id`, `model_version` — точное совпадение;
- `from`, `to` — включительные границы времени события в RFC3339;
- `limit` — 1–200, по умолчанию 50; `offset` — от 0.

Повторные, неизвестные, пустые и некорректные фильтры отклоняются. Карточка показывает сохранённые данные и не позволяет изменять сообщение или принимать кредитное решение. Список не содержит ранние отказы/`NEED_INFO` МС1 и не является журналом всех оценок.

## Проверка

Проверяются все исходные примеры уведомлений и три типа `value`. PostgreSQL-тесты под тегом `integration` проверяют реальный вход/доступ, запись и чтение, фильтры, непрозрачные ID, повтор, конфликт, конкурентные одинаковые/разные сообщения, отказ вставки и отложенную ошибку commit. Сценарий с настоящими операциями МС2 и REST-клиентом теряет первый ACK после фиксации: выдача остаётся одна, повтор передаёт те же байты и получает подтверждение, последующий вызов повторно не отправляет событие.
