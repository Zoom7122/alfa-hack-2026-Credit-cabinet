# MVP: состояние банка и проверки МС2

МС2 проверяет одну сделку, предложенную МС1, на текущем состоянии банка. Правила одинаковы для ИП и ЮЛ. Основа — «Экономика_и_нормативы.xlsx»; ниже зафиксирована упрощённая учебная модель. Пороги — настройки демонстрации, а не описание полного действующего банковского регулирования.

## 1. Что получает и хранит МС2

По REST/JSON МС1 передаёт ID заявки и заёмщика, тип заёмщика, сумму, срок в месяцах, годовую ставку, результат скоринга и маршрут. Для ручного маршрута передаются также причины. Точные REST-контракты определены в [OpenAPI](../contracts/openapi.json).

| Маршрут от МС1 | Действие МС2 |
|---|---|
| Предварительное одобрение | Рассчитать состояние после выдачи, проверить ограничения; при успехе учесть учебную выдачу. |
| Ручное рассмотрение | Передать заявку, запрос клиента и причины в МС3. Банковские расчёты не запускать, кредит не выдавать. |

Недостаток данных и отказ завершаются в МС1. Такие заявки в МС2 не поступают.

Текущими банковскими величинами владеет только МС2. Статическая политика экономики и риска общая для МС1/МС2; сервисы А и Б банковские значения не передают. При запуске МС2 устанавливается следующий фиксированный учебный набор. **Денежные значения таблицы — млн руб.; внутри расчётов используются рубли.**

| Величина | Смысл | Начальное значение |
|---|---|---:|
| K1 / Ka / K0 | Базовый / основной / совокупный капитал | 650 / 800 / 1 000 |
| RWA11 / RWA12 / RWA10 | Базы риска для Н1.1 / Н1.2 / Н1.0 | По 8 000 |
| Lam / Lat | Высоколиквидные / ликвидные активы | 600 / 2 500 |
| D2 / D3 | Базы обязательств для Н2 / Н3 | 2 000 / 4 000 |
| Krd | Долгосрочные кредитные требования для Н4 | 1 500 |
| Funding4 | Долгосрочное фондирование в знаменателе Н4 | 1 000 |
| Invest | Вложения в доли и акции для Н12 | 150 |
| Cash / CashMin | Доступные для выдачи средства / внутренний минимум | 10 / 6 |
| Reserves | Уже сформированные резервы | 50 |
| Реестр групп | Риск по группам связанных заёмщиков | g1: 200; g2: 180; related: 100; small: 20 |
| Связь с банком | Группа, связанная с самим банком, для Н25 | related |
| Реестр новых выдач | ID заявки, кредита, заёмщика и условия | Пустой |
| Разрешение выдачи | Общий внутренний запрет/разрешение | Выдача разрешена |

Cash — доступная для этого продукта часть ликвидных активов; контроль CashMin дополняет Н2 и Н3. Уже сформированные резервы учтены в начальном капитале и повторно из него не вычитаются.

Принадлежность заёмщиков к группам задаётся учебным справочником МС2. Независимый новый заёмщик образует свою группу с исходным риском 0. Связанность заёмщиков между собой и связанность с банком — разные признаки.

Состояние хранится в памяти между запросами. Перезапуск возвращает начальный набор. Проценты нормативов каждый раз вычисляются из денежных величин; отдельные сохранённые проценты не «поправляются» вручную.

## 2. Как выдача меняет состояние

Обозначения: P — сумма кредита, n — срок, r — годовая ставка; q — доля резерва; C0 — разовый расход банка. Для MVP кредит рублёвый, аннуитетный, без залога и гарантии.

Чтобы не вводить отдельную модель банковского риска, профиль новой сделки фиксирован: **категория качества II, q = 5%, вес риска RW = 100%, годовая PD = 4%, LGD = 45%**. Это учебные настройки, а не результат определения категории по реальным банковским правилам. Класс скоринга A/B и категория качества I–V не отождествляются.

МС2 сначала строит копию состояния. Новый резерв R = q × P; чистое требование E = P − R.

| Величина | Изменение в расчётной копии | Причина |
|---|---|---|
| Reserves | +R | Резерв по новому кредиту. |
| K1, Ka, K0 | Каждая −R − C0 | Резерв и расход уменьшают прибыль и капитал. |
| RWA11, RWA12, RWA10 | Каждая +E × RW | Новый кредит добавляет риск. |
| Cash, Lam, Lat | Каждая −P − C0 | Выдача и разовый расход расходуют средства. |
| Krd | +B12 × (1 − q), если n > 12; иначе без изменения | B12 — остаток основного долга после 12 платежей; учебное приближение долгосрочной части. |
| Риск группы заёмщика | +E | Кредит увеличивает требования к группе. |
| D2, D3, Funding4, Invest | Без изменения | Новое фондирование и покупки вложений в этом сценарии отсутствуют. |

Резерв сам по себе не является денежным платежом и не вычитается из ликвидности. Будущие процентные доходы не прибавляются к капиталу в момент выдачи. Выделенный под сделку капитал используется в оценке доходности, но дополнительно из K0 не вычитается.

График нужен для B12 и экономики: месячная ставка i = r / 12, платёж A = P × i / (1 − (1 + i)^(−n)); при нулевой ставке A = P / n. Остаток долга уменьшается на часть платежа, погашающую основной долг.

## 3. Нормативы и ограничения

В таблице отношения показаны в процентах. В config/ и REST/JSON значения нормативов и их границы передаются долями единицы: Н2 = 0.30 означает 30%, а не 0,30%. Проверяются **значения после предполагаемой выдачи**. Равенство границе допустимо.

| Проверка | Формула | Граница MVP | Влияние выдачи |
|---|---|---|---|
| Н1.1 — достаточность базового капитала | K1 / RWA11 | ≥ 6,5% | Капитал падает, база риска растёт. |
| Н1.2 — достаточность основного капитала | Ka / RWA12 | ≥ 8% | То же. |
| Н1.0 — достаточность совокупного капитала | K0 / RWA10 | ≥ 10% | То же. |
| Н2 — мгновенная ликвидность | Lam / D2 | ≥ 15% | Lam уменьшается. |
| Н3 — текущая ликвидность | Lat / D3 | ≥ 50% | Lat уменьшается. |
| Н4 — долгосрочная ликвидность | Krd / (K0 + Funding4) | ≤ 120% | Долгосрочное требование может вырасти, капитал падает. |
| Н6 — риск на одну группу | Максимальный риск группы / K0 | ≤ 24,8% | Риск получателя растёт; доли остальных групп тоже растут из-за снижения K0. |
| Н7 — совокупность крупных рисков | Сумма крупных рисков / K0 | ≤ 800% | Может вырасти риск группы и измениться состав крупных групп. |
| Н25 — риск на связанную с банком группу | Максимальный риск такой группы / K0 | ≤ 20% | Растёт при выдаче связанной группе и при снижении K0. |
| Н12 — вложения в доли и акции | Invest / K0 | ≤ 25% | Invest неизменен, но снижение K0 повышает отношение. |

Для Н1 взяты исходные минимумы 4,5% / 6% / 8% и общая учебная надбавка 2 процентных пункта: поддержание капитала 1, контрциклическая надбавка 0,5, внутренний запас 0,5. Для Н6 используется внутренний предел 24,8% вместо исходного максимума 25%. Эти границы хранятся в настройках.

**Крупный риск для Н7 — риск группы строго больше 5% от K0 после выдачи.** В сумму входит весь риск такой группы. Пересчитываются все группы: снижение капитала может сделать крупным даже ранее существовавший риск. Н6 также проверяется по всем группам. При отсутствии связанных с банком групп Н25 = 0.

Начальный набор проходит проверки: Н1.1 = 8,125%; Н1.2 = 10%; Н1.0 = 12,5%; Н2 = 30%; Н3 = 62,5%; Н4 = 75%; Н6 = 20%; Н7 = 48%; Н25 = 10%; Н12 = 15%.

Дополнительные ограничения:

| Контроль | Условие успешной выдачи |
|---|---|
| Средства на выдачу | Cash после выдачи ≥ CashMin = 6 млн руб. |
| Качество ссуды | Категория не хуже III; в стандартном профиле MVP всегда II. |
| Внутреннее разрешение | Выдача разрешена настройкой банка. |
| Экономика | NPV строго > 0. |
| Корректность расчёта | Нет отрицательных активов/капитала и недопустимых знаменателей. |

Нулевой или отрицательный знаменатель не превращается в «хороший» нулевой норматив. Если недопустимое состояние возникает из-за предложенной сделки, это проблема банка и выдачи нет. Некорректная исходная конфигурация или неверный REST-запрос — техническая ошибка; они не обозначают отказ заёмщику или финансовую проблему банка.

## 4. Экономика сделки

МС2 проверяет доходность на предложенных условиях. Ту же чистую функцию экономики МС1 использует для автоматического подбора на общих статических параметрах, без доступа к текущему состоянию банка. Кредитная ставка приходит по REST в процентах (24 означает 24%) и перед расчётом делится на 100. Ставки, PD и LGD в формулах и config/policy.json задаются долями единицы. Учебные параметры:

| Параметр | Значение |
|---|---:|
| Стоимость фондирования FTP | 15% годовых; при сроке > 24 месяцев — 15,5% |
| Операционные расходы | 1% годовых от остатка долга |
| Ожидаемые потери | PD × LGD = 4% × 45% годовых от остатка |
| Выделенный капитал | 12% от чистого требования, взвешенного по риску |
| Годовая цена выделенного капитала | 20% |
| Годовая ставка дисконтирования d | 15% |
| Разовый расход C0 | 0 руб. в основном демо |

Для месяца t, где B_t — долг на начало месяца:

- Процентный доход I_t = B_t × r / 12.
- Фондирование F_t = B_t × FTP / 12; операционные расходы O_t = B_t × 1% / 12.
- Ожидаемые потери EL_t = B_t × PD × LGD / 12.
- Выделенный капитал K_t = B_t × (1 − q) × RW × 12%; его стоимость CC_t = K_t × 20% / 12.
- Маржа M_t = I_t − F_t − O_t − EL_t − CC_t.

**NPV = −C0 + Σ [M_t / (1 + d)^(t/12)], t = 1…n.** Итоговый NPV после суммирования округляется один раз до копейки. При NPV ≤ 0 выдача не подтверждается.

Резерв уменьшает капитал в разделе 2; в NPV потери учитываются через EL_t, резерв повторно расходом не списывается. Тело кредита отдельно из NPV маржи не вычитается: возвратный основной долг и его финансирование учтены через график и FTP.

Справочный годовой RAROC: приведённая маржа до стоимости капитала, включая −C0, делится на Σ [(K_t / 12) / (1 + d)^(t/12)]. Отдельного блокирующего порога RAROC в MVP нет.

## 5. Результат проверки и изменение состояния

| Результат | Ответ МС1 клиенту | Состояние МС2 | Уведомление МС3 только от МС2 |
|---|---|---|---|
| Все проверки успешны | Одобрено | Сохранить расчётную копию и запись о кредите: это учебная выдача. | ID заявки и кредита, заёмщик, сумма и условия выдачи. |
| Есть банковская проблема | Заявка на рассмотрении | Отбросить копию; ничего не выдавать. | Заявка и условия; все нарушения, значения до/после и допустимые границы. |
| Пришёл ручной маршрут | Заявка на рассмотрении | Не выполнять проверку выдачи и не менять финансовые величины. | Заявка, запрос клиента и причины ручного решения. |

Проверка и сохранение выполняются последовательно на актуальном состоянии, чтобы две заявки не использовали один остаток средств. Повтор уже учтённой заявки возвращает прежний результат выдачи без повторного списания и повторной отправки подтверждённо доставленного уведомления. Недоставленное событие PENDING повторяется с прежним ID по [правилам доставки](05_integration.md). Для MVP достаточно реестра ID в памяти.

**Иллюстрация UC-06 для заранее заданных сделок.** Это проверка банковской математики, не результат оптимизатора. Полные выбранные предложения приведены в testdata/. Два независимых заёмщика, оба предварительно одобрены МС1; каждый кредит — на 24 месяца под 24% годовых. Остальные настройки — из этого файла.

| Шаг | Сумма | Cash до → расчётный Cash после | Резерв новой сделки | NPV | Результат и сохранённый Cash |
|---|---:|---|---:|---:|---|
| Первая заявка | 3 млн руб. | 10 → 7 млн руб. | 150 тыс. руб. | +118 945,54 руб. | Одобрено; сохранено 7 млн руб. |
| Вторая заявка | 2 млн руб. | 7 → 5 млн руб. | 100 тыс. руб. | +79 297,03 руб. | На рассмотрении: 5 < 6; сохранено 7 млн руб. |

Остальные ограничения в обеих проверках выполнены. После первой выдачи K0 = 999,85 млн руб., RWA10 = 8 002,85 млн руб., Reserves = 50,15 млн руб. После второй проверки эти сохранённые значения не меняются.

## 6. Границы учебной модели

- Проверка платёжеспособности, DSCR/DSR, денежных потоков заёмщика и подбор суммы, срока, ставки остаются в МС1. МС2 не повторяет скоринг и не перебирает альтернативные сделки.
- Из Excel сохраняются контроль капитала, ликвидности, концентрации, резервов и экономики. Упрощаются базы риска и обязательств, отнесение долга к долгосрочному, оценка ожидаемых потерь; не моделируется помесячная вероятность дожития кредита.
- Несколько режимов резервирования, переуступка риска на поручителя, залог, гарантии и сложные регуляторные расчёты не включаются. Н18, Н26/Н27, валютные, отраслевые, макропруденциальные и консолидированные ограничения не рассчитываются. Общий флаг разрешения выдачи — внутреннее правило демо, а не замена этим проверкам.
- Между заявками нет течения времени, погашений, начисления доходов и новых источников фондирования. Подтверждение считается учебной выдачей. Реальные платежи, решение сотрудника и устранение проблем банка за пределами MVP.

Go DTO находятся в [contract.go](../contracts/contract.go), маршруты и требования к соседним сервисам описаны в [руководстве интеграции](05_integration.md).
