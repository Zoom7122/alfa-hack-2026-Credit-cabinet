# Поставщик дополнительных фактов и версии моделей

Этот документ определяет REST-контракт расширения Credit Engine. Схемы опубликованного комплекта — в [OpenAPI поставщика](../contracts/scoring_facts.openapi.json), проверочные примеры — в [JSON-примерах](../contracts/examples/scoring_facts.json) и [демонстрационной схеме](../contracts/examples/scoring_facts.openapi.json). API МС1/МС2 описан в [основном OpenAPI](../contracts/openapi.json). Рабочий МС1 использует поставщика только для compiled-моделей, которым нужны новые факты; наличие общей схемы само по себе не включает вызов.

## 1. Ответственность и один запрос

МС1 самостоятельно отправляет один `POST /api/v1/scoring-facts` за всем блоком дополнительных исходных чисел и boolean выбранной модели. Поставщик агрегирует сведения из mock-api и других систем. Отдельных запросов для каждого поля нет. Отправитель А передаёт выбор версии и прежние исходные данные; значения новых полей из запроса А не используются.

Если модель не использует поставщика, обращения нет. Базовые `ip-v2` и `legal-v2` продолжают работать без нового URL. Подтверждённый ранний стоп прекращает дальнейшие обращения. Стоп по полученным фактам проверяется до отчётности Б и до проверки полноты; неизвестный факт сам по себе стопом не является.

## 2. Версии и выбор модели

| Идентификатор | Назначение |
|---|---|
| `model_version` | Полный неизменяемый идентификатор версии скоринга, например `ip-v2`; уникален в каталоге сборки и связан с типом заёмщика. Это также значение `score.model`. |
| `facts_schema_version` | Неизменяемый идентификатор именованной схемы ответа поставщика. Сопоставляется с моделью в комплекте релиза. |
| Идентификатор релиза и SHA256 | Фиксируют комплект определений, кода и документации; подготовленный релиз отличается от запущенной сборки. |
| `policy_id` | Версия банковской экономики; не подменяет версию модели и не меняется автоматически при редактировании скоринга. |

Новый запрос А к `POST /api/v1/decisions` явно содержит строковое поле `model_version` рядом с `application_id`. Сам блок заявки остаётся прежним. Например, `"model_version": "ip-v2"` явно выбирает сохранённую модель ИП. Для нового опубликованного определения используется его точный идентификатор из каталога поддерживаемых версий сборки.

- Поле отсутствует: выбрать `ip-v2` для SOLE_PROPRIETOR или `legal-v2` для LEGAL_ENTITY; это постоянное правило совместимости, не псевдоним «последняя».
- `null` или неверный JSON-тип версии: 400 `INVALID_JSON`.
- Пустая/пробельная, неизвестная, неподдерживаемая либо принадлежащая другому типу заёмщика версия: 422 `UNSUPPORTED_MODEL_VERSION`, `fields=["model_version"]`.
- После успешного выбора точный идентификатор возвращается в HTTP-заголовке `X-Scoring-Model-Version`, в том числе при `score=null`, раннем отказе, NEED_INFO и технической ошибке зависимости. Если технический разбор или выбор версии не состоялся, заголовок отсутствует.
- При полном балле `score.model` совпадает с заголовком. JSON существующего DecisionResponse не расширяется обязательными метаданными, поэтому сохранённые ответы v2 остаются эталонами.

Первый переход сохраняет v2 и новую версию одновременно. Удаление поддержки — явное изменение следующей сборки. Неизвестную версию нельзя подменить поддерживаемой. Предварительный расчёт черновика не делает его доступным в работающем МС1.

## 3. Запрос МС1 → поставщик

Content-Type: `application/json`. Все четыре поля верхнего уровня обязательны, не допускают `null`; неизвестные поля запрещены. Объект borrower обязателен и содержит ровно перечисленные ключи.

| Поле | Тип и правило |
|---|---|
| `application_id` | Непустая строка, идентификатор исходной заявки без замены или генерации. |
| `borrower.id` | Непустой исходный идентификатор заёмщика. |
| `borrower.type` | SOLE_PROPRIETOR либо LEGAL_ENTITY. |
| `borrower.inn` | Строка исходного ИНН либо явный `null`, если бизнес-сведение неизвестно. Ключ присутствует в обоих случаях. Новые паспортные/форматные бизнес-проверки этот протокол не вводит. |
| `model_version` | Точная выбранная поддерживаемая версия. |
| `facts_schema_version` | Схема из встроенного соответствия выбранной модели; А её не назначает. |

Имя/пожелания по кредиту/все поля анкеты не пересылаются поставщику без потребности. Нет автоматически меняющихся evaluation_date, request_id, timestamp и случайных значений. МС1 не делает скрытых повторных попыток внутри одного обращения.

Пример использует вымышленные версии и поля, не является новой действующей моделью и не задаёт баллы:

```json
{
  "application_id": "app-facts-demo-001",
  "borrower": {
    "id": "borrower-demo-001",
    "type": "SOLE_PROPRIETOR",
    "inn": "990000000001"
  },
  "model_version": "ip-demo-v1",
  "facts_schema_version": "demo-facts-v1"
}
```

## 4. Ответ поставщика

Успех — только HTTP 200 и один JSON-объект. Оболочка не допускает лишних ключей. Все семь ключей обязательны и не допускают `null`.

| Поле | Тип и правило |
|---|---|
| `application_id` | В точности из запроса. |
| `borrower_id` | В точности borrower.id запроса. |
| `borrower_type` | В точности borrower.type запроса. |
| `model_version` | В точности выбранная версия из запроса. |
| `facts_schema_version` | В точности ожидаемая версия схемы из запроса. |
| `facts_date` | Существующая календарная дата YYYY-MM-DD, дата сведений; не позднее даты оценки. При повторе не обновляется автоматически. |
| `additional_facts` | Объект с именованными полями точной сгенерированной схемы. Даже при неизвестных значениях сам объект не равен null. |

Пример известных нулевого и отрицательного логического ответа:

```json
{
  "application_id": "app-facts-demo-001",
  "borrower_id": "borrower-demo-001",
  "borrower_type": "SOLE_PROPRIETOR",
  "model_version": "ip-demo-v1",
  "facts_schema_version": "demo-facts-v1",
  "facts_date": "2026-10-20",
  "additional_facts": {
    "annual_contract_value_rub": 0,
    "has_confirmed_contracts": false
  }
}
```

В примере оба ключа additional_facts обязательны для транспорта и nullable; annual_contract_value_rub объявлен обязательным бизнес-фактом только для иллюстрации. Реальные имена, типы, единицы, домены и бизнес-обязательность берутся из опубликованной модели, а Go-структуры/схемы генерируются вместе. В МС1 не применяется универсальная map вместо именованного DTO.

Каждый объявленный ключ передаётся явно, включая необязательные для бизнес-решения факты: `null` обозначает неизвестность. Отсутствие ключа отличается от `null` и означает нарушение схемы. Неизвестные ключи, несовместимый JSON-тип или выход за объявленный допустимый домен — техническая ошибка. В частности, строка `"false"` не boolean, строка `"100"` не число. Числа конечны; NaN/Infinity не являются допустимым JSON. Повторяющиеся ключи и второй JSON-документ после первого запрещены.

У каждого числового поля определены единицы; проценты не превращаются автоматически в доли. Новые параметры не являются готовыми score/grade/коэффициентами. Существующие показатели рассчитывает МС1 прежними формулами. Правила актуальности сверх проверки корректности/будущей даты задаются явно моделью; новый произвольный порог давности этот протокол не вводит.

Один и тот же полученный блок используется всеми правилами одного расчёта; повторное обращение ради другой оценки того же параметра запрещено.

## 5. Порядок проверки и ошибки

Сначала проверяются HTTP/JSON и оболочка; затем соответствие ID/типу заёмщика, версиям и дате; затем именованный блок по точной схеме. После технической проверки выполняются подтверждённые стопы, полнота/бизнес-обязательность и остальные правила модели в установленном порядке.

| Ситуация | Ответ МС1 | Код |
|---|---|---|
| Обязательный бизнес-факт явно null, более приоритетного подтверждённого стопа нет | 200 NEED_INFO, score=null, без МС2/МС3 | MISSING_DATA, поле additional_facts.<имя> |
| Известное 0/false | Продолжить обычный расчёт модели | Не ошибка |
| Нет обязательного ключа оболочки/именованного блока, null вместо объекта, неверный JSON/тип/дата/домен, лишний или повторяющийся ключ | 502 | INVALID_FACTS_RESPONSE |
| Чужой application_id/borrower_id/borrower_type | 502 | FACTS_ID_MISMATCH |
| Не совпала модель или схема | 502 | FACTS_VERSION_MISMATCH |
| Соединение недоступно, редирект, неожиданный статус, в том числе 204/400/404/422/500/503 | 502 | FACTS_UNAVAILABLE |
| Истёк тайм-аут | 504 | DEPENDENCY_TIMEOUT |

404 поставщика не имеет специального бизнес-смысла: отсутствие факта передаётся HTTP 200 с явным null. Техническая ошибка поставщика не становится REJECTED, UNDER_REVIEW или NEED_INFO. Ошибки МС1 используют существующий Problem с безопасными detail и путями fields; тело/адрес поставщика и секреты не выдаются клиенту. Отмена входного контекста прерывает запрос без скрытых повторов или банковских действий.

## 6. Повторы и изменения данных

Идентичность — одинаковые значения четырёх полей запроса и всех вложенных полей borrower; порядок ключей и форматирование JSON значения не имеют. Поставщик возвращает одинаковые значения всего ответа, включая facts_date и null. Изменения данных в источниках сами по себе не меняют ответ идентичному запросу.

МС1 не хранит снимок ответа и не добавляет изменяющийся маркер для обновления данных. Для осознанной новой оценки с изменившимися сведениями нужна новая заявка с новым application_id либо другое согласованное содержание запроса. Подменять версию ради «обновления» или повторять уже учтённую заявку как новую нельзя.

Повтор после обновления сборки явно выбирает прежнюю поддерживаемую версию. Реестр выдач остаётся только в МС2: идентичная операция не создаёт вторую выдачу, другая операция с уже зарегистрированным application_id даёт 409. Выбор другой модели не обходит эту защиту. Неизменившийся ответ поставщика не означает обещание одинакового решения при произвольной смене остальных входов/даты оценки/банковского состояния.

## 7. Настройки и выпуск

Настройки подключения: `FACTS_URL` — базовый HTTP(S) URL по тем же правилам, что остальные зависимости; `FACTS_TIMEOUT` — положительная Go duration, по умолчанию 2s. Они используются реализованным REST-клиентом. Если ни одна поддерживаемая модель не использует поставщика, FACTS_URL не требуется; модель, которой нужны факты, не должна работать с отсутствующей зависимостью.

В общем бюджете учитываются FACTS_TIMEOUT + STATEMENTS_TIMEOUT + BANK_TIMEOUT; HTTP_WRITE_TIMEOUT должен быть строго больше суммы. При стандартных 2s + 2s + 4s серверные 15s оставляют запас на расчёт и сериализацию. МС2 → МС3 имеет собственный тайм-аут 2s внутри операции МС2; он не добавляется второй раз к бюджету МС1.

Настройки/клиент реализованы согласно [описанию FactsClient](18_facts_client.md). Если FACTS_URL не настроен и поставщик не используется, сохраняется прежний бюджет STATEMENTS_TIMEOUT + BANK_TIMEOUT. При настроенном URL учитываются все три зависимости; необходимость URL для поддерживаемых моделей дополнительно проверяется при сборке приложения.

Соответствие model_version → borrower_type/facts_schema_version/Go-тип/SHA256 включается в статический каталог релиза. Изменения именованных полей или доменов создают новую схему; изменение только весов может использовать прежнюю совместимую схему, но создаёт новую версию модели. До обновления МС1 поставщик должен поддерживать новую пару версий; старые пары сохраняются на период совместимости. Неподдерживаемая пара на стороне поставщика даёт техническую ошибку МС1, а не переход к другому формату.

ScoringFactsResponseEnvelope задаёт только общую оболочку. Для реального выпуска обязательна точная именованная схема выбранной версии; одной оболочки недостаточно. Генератор выпускает строгие именованные схемы и oneOf по опубликованным парам версий. Если модели комплекта не используют поставщика, его OpenAPI содержит пустой paths: новый вызов не заявляется. ExampleNamedFacts и ip-demo-v1/legal-demo-v1 сохранены отдельно в демонстрационной схеме и не становятся действующими моделями.

## 8. Проверка интеграции

Корпус примеров содержит успешные ИП/ЮЛ, 0/false/null, отсутствие ключей, неверные типы/домены/ID/версии/даты, лишние поля, статусы и сетевые ошибки. При реализации DTO/клиента дополнительно проверяются некорректный JSON, дубли ключей, второй документ, превышение ограничения тела, отмена контекста, один запрос и идентичный повтор. Полный процесс должен подтвердить отсутствие вызова для v2/раннего стопа и отсутствие МС2 при технической ошибке или NEED_INFO.

Ни формат примера, ни доступность нового поставщика не заменяют [приёмку модели v2](07_acceptance.md) и проверку прохождения boolean до событий МС3.
