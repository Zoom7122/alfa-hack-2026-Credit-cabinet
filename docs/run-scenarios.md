# Запуск и сценарии демонстрации кредитного кабинета

Актуальность: 26.10.2026. Команды выполняются из корня репозитория, если рядом не указан другой каталог. Данные пользователей, компаний, токены `demo-*` и документы в `examples/` — синтетические.

Здесь собраны режимы запуска, все тестовые пользователи, сценарии A–E, действия банка, готовые демо-заявки, проверки подписи и отдельные сценарии credit-engine. Ожидаемое поведение взято из исходников, JSON-примеров и тестов. Документ не является отчётом об успешном прогоне всех сценариев на текущей базе.

## 1. Быстрый запуск полного кабинета

Нужны Docker с Compose и `make`. Локальные Go и Node для контейнерного запуска не требуются.

1. Выполнить `make env`. Команда создаёт `.env` из `.env.example`, только если файла ещё нет.
2. Установить в корневом `.env`:

   ```dotenv
   FRONTEND_API_MOCK=true
   FRONTEND_COLLECTOR_MOCK=false
   FRONTEND_API_UPSTREAM=http://api:8080
   FRONTEND_COLLECTOR_UPSTREAM=http://data-collector:8081
   ```

3. Выполнить:

   ```bash
   make up
   make ps
   ```

4. Открыть [кабинет](http://localhost:3000/login).
5. Для первой заявки выбрать **Ковалёва Игоря Сергеевича**, затем пройти сценарий A из раздела 7.

Это рекомендуемый режим: регистрация, анкета, сбор данных, проверка подписи, скоринг и рабочее место банка используют настоящий backend проекта. Ответы внешних систем предоставляет контейнер `mock-api`. Старые демо-экраны `/api/v1` обслуживаются моками MSW в браузере.

**После изменения `FRONTEND_*_MOCK` нужна пересборка:**

```bash
docker compose up -d --build frontend
```

Затем обновить страницу. Одного `docker compose restart frontend` недостаточно: флаги встраиваются в JavaScript при сборке.

## 2. Все режимы запуска

### 2.1. Как выбрать настройки

| Режим | `FRONTEND_API_MOCK` | `FRONTEND_COLLECTOR_MOCK` | Для чего |
|---|---|---|---|
| Полный стек с живым data-collector | `true` | `false` | Основная демонстрация A–E, Kafka, БД, подписи, credit-engine, андеррайтер |
| Полностью браузерная демонстрация | `true` | `true` | Интерфейс без backend, предсказуемые демонстрационные исходы |
| Только живой data-collector | `false` | `false` | Работа с backend без старых демо-заявок, задач подписания и WebSocket основного API |
| Только мок data-collector | `false` | `true` | Браузерная демонстрация новых заявок A–E без старых демо-заявок |

В актуальных исходниках `VITE_API_MOCK=false` отключает старые списки/профиль/статусы основного API, его WebSocket и доступ к старым страницам заявок. Это режим без legacy-демонстрации, а не переключатель на существующий отдельный сервис `api`. После изменения исходников обязательно пересобрать frontend: прежний образ мог продолжать слать запросы к отсутствующему `api:8080` и получать 502.

`/api/v1` и `/collector/api/v1` имеют разные контракты. Нельзя просто направить основной API на data-collector и считать интеграцию завершённой. Для режима только живого data-collector поставить оба флага в `false` и выполнить `make up`; готовые сценарии раздела 9 тогда недоступны.

### 2.2. Только frontend в Docker, оба API на моках

В корневом `.env`:

```dotenv
FRONTEND_API_MOCK=true
FRONTEND_COLLECTOR_MOCK=true
```

```bash
make front
```

Адрес: [http://localhost:3000](http://localhost:3000). Backend для этого режима не нужен. Данные сохраняются в браузере, а не в PostgreSQL. Уже работающие контейнеры других сервисов `make front` не останавливает.

### 2.3. Frontend локально, backend в Docker

Сначала поднять полный стек по разделу 1. Затем открыть отдельный терминал:

```bash
cd frontend
nvm use
npm ci
VITE_API_MOCK=true VITE_COLLECTOR_MOCK=false \
  COLLECTOR_PROXY_TARGET=http://localhost:8081 \
  npm run dev -- --host 127.0.0.1 --port 5173
```

Адрес: [http://localhost:5173](http://localhost:5173). Требуется Node `24.22.x` из `frontend/.nvmrc`; если Node уже установлен нужной версии, шаг `nvm use` можно пропустить.

Для локального frontend без backend заменить `VITE_COLLECTOR_MOCK=false` на `true`. Корневые `FRONTEND_*` управляют сборкой Docker, а `VITE_*` — локальным frontend. Вместо префикса команды можно записать `VITE_API_MOCK=true` и нужный `VITE_COLLECTOR_MOCK` в `frontend/.env.local`.

Моки MSW требуют `localhost` либо HTTPS. При открытии по `http://<IP>` Service Worker может не запуститься: запросы уйдут в nginx и основной API вернёт 502.

### 2.4. Backend без frontend, для Swagger и curl

С настройками подключения к БД из корневого `.env`:

```bash
make env
docker compose up -d --build \
  postgres kafka migrate mock-api \
  data-collector data-collector-publisher data-collector-worker \
  data-collector-signature-worker data-collector-decision-worker \
  credit-engine-scoring credit-engine-bank
```

Swagger и HTTP-запросы доступны на порту 8081. Для сбора нужны publisher и worker; для итогового решения — также decision-worker и оба сервиса credit-engine. Один запущенный `data-collector` ещё не означает, что задача пройдёт весь конвейер.

Отдельные Go-процессы при разработке запускаются из `data-collector/`:

| Процесс | Команда | Основные настройки окружения |
|---|---|---|
| HTTP API | `make run` | `DATABASE_URL`, `HTTP_ADDR`, `MOCK_API_URL`, `DOCUMENTS_DIR` |
| Outbox publisher | `make run-publisher` | `DATABASE_URL`, `KAFKA_BROKERS` |
| Worker сбора и финансовых документов | `make run-worker` | `DATABASE_URL`, `KAFKA_BROKERS`, `MOCK_API_URL`, `DOCUMENT_STORAGE_PATH` |
| Worker подписи | `make run-signature-worker` | `DATABASE_URL`, `KAFKA_BROKERS`, `DOCUMENTS_DIR`, тестовый trust-каталог |
| Worker решений | `go run ./cmd/decision-worker` | `DATABASE_URL`, `SCORING_URL`, `DEMO_EVALUATION_DATE` |

Каждый процесс — в отдельном терминале. Сначала нужны миграции, PostgreSQL, Kafka и зависимости. Пути хранения файлов у API и обработчиков должны указывать на одни файлы; адреса из Compose вида `kafka:9092` предназначены для контейнеров, а с хоста используется `localhost:9094`. Не запускайте локальный API на занятом контейнером порту 8081.

## 5. Как заполнять новую заявку

1. Войти нужным пользователем из раздела 3.
2. Открыть «Новая заявка» / каталог, выбрать продукт, сумму и срок, перейти к оформлению.
3. **Компания:** ввести ИНН из таблицы сценариев. Дождаться подсказки реквизитов. Проверить ФИО представителя и роль.
4. **Сумма, срок и цель:** использовать значения из раздела 6.
5. **Руководитель и анкета:** возраст, семейное положение, дети, ФИО, ИНН и дата рождения руководителя. Для ИП — сам предприниматель.
6. **Для оценки:** заполнить таблицу из раздела 6.2, если нужен полный расчёт. Поля разрешено пропустить, но живой движок тогда может запросить их отдельно.
7. **Счета и площадки:** добавить БИК, токены маркетплейсов и ОФД, когда они предусмотрены сценарием.
8. **Залог:** в B можно указать объекты из раздела 6.3; в остальных базовых сценариях оставить пустым.
9. **Документы:** для A загрузить оригинал и подпись вместе; выбрать оригиналу тип «Бухгалтерская отчётность». Подпись связывается с оригиналом по имени.
10. **Согласия и отправка:** отметить согласия компании на БКИ, руководителя на БКИ, на получение налоговой отчётности; для налогового согласия оставить декларации и ЕНС. У бухгалтера A указать МЧД и ИНН представителя. Нажать «Отправить заявку».

В UI даты рождения вводятся как `19.07.1984`, в JSON — `1984-07-19`. Суммы — в рублях, срок — в месяцах. Ставка `28` означает 28 %, а не 0,28.

Поля анкеты до отправки и файлы черновика хранятся в браузере. После отправки исходную анкету повторно отправить нельзя; уточнения передаются ответами на вопросы банка. Чужие черновики коллеги не предназначены для продолжения от другого пользователя.

## 11. A–E через API: готовые команды и тела

Для ручного Swagger: открыть `/api/v1/applicants`, выполнить регистрацию, скопировать **id заявки `app_…`** из ответа и передать его в `/api/v1/applications/{id}/questionnaire`. ИНН, id компании `apl_…` и id заявки `app_…` не взаимозаменяемы.

Исходные файлы предназначены прежде всего для сбора. У B–E в JSON нет запрошенных суммы/срока/продукта, а блок `scoring` отсутствует у всех пяти. Прямая отправка этих файлов не является полным вводом для итогового расчёта.

Ниже команда создаёт временную копию анкеты с данными из таблиц, не меняя файлы проекта. Нужны Bash, `curl` и `jq`. Выполнить из корня; для другого сценария поменять только `SCENARIO` на `b`, `c`, `d` или `e`. Создаются настоящие записи в БД демонстрационного стека.

```bash
(
set -e
SCENARIO=a
DEMO_API=http://localhost:8081/api/v1
DEMO_DIR=$(mktemp -d /tmp/credit-scenario.XXXXXX)

case "$SCENARIO" in
  a) DEMO_USER=usr_accountant_north; AMOUNT=5000000; TERM=24; MAX_TERM=36; OWN=500000; FREE=100000; CASH_MIN=20000; EXPERIENCE=8 ;;
  b) DEMO_USER=usr_director_stroyresurs; AMOUNT=8000000; TERM=36; MAX_TERM=48; OWN=800000; FREE=50000; CASH_MIN=20000; EXPERIENCE=8 ;;
  c) DEMO_USER=usr_director_altair; AMOUNT=5000000; TERM=24; MAX_TERM=36; OWN=500000; FREE=100000; CASH_MIN=20000; EXPERIENCE=8 ;;
  d) DEMO_USER=usr_ip_smirnova; AMOUNT=1000000; TERM=12; MAX_TERM=24; OWN=100000; FREE=20000; CASH_MIN=10000; EXPERIENCE=3 ;;
  e) DEMO_USER=usr_finance_techno; AMOUNT=5000000; TERM=24; MAX_TERM=36; OWN=500000; FREE=100000; CASH_MIN=20000; EXPERIENCE=8 ;;
  *) printf 'Допустимые сценарии: a b c d e\n' >&2; exit 1 ;;
esac

DEMO_TOKEN=$(curl --fail-with-body -sS "$DEMO_API/auth/mock-login" \
  -H 'Content-Type: application/json' \
  -d "{\"user_id\":\"$DEMO_USER\"}" | jq -er '.token')

APPLICATION_ID=$(curl --fail-with-body -sS "$DEMO_API/applicants" \
  -H "Authorization: Bearer $DEMO_TOKEN" -H 'Content-Type: application/json' \
  --data-binary "@data-collector/examples/scenario-$SCENARIO.applicant.json" | jq -er '.id')

jq --arg scenario "$SCENARIO" --argjson amount "$AMOUNT" --argjson term "$TERM" \
  --argjson maxterm "$MAX_TERM" --argjson own "$OWN" --argjson free "$FREE" \
  --argjson cashmin "$CASH_MIN" --argjson experience "$EXPERIENCE" '
  .product_code = "WORKING_CAPITAL" |
  .requested = {amount: $amount, term_months: $term} |
  .purpose = {code: "WORKING_CAPITAL", description: "Закупка товара под сезон"} |
  .scoring = {
    max_annual_rate: 28, min_acceptable_amount: ($amount * 3 / 10),
    max_acceptable_term_months: $maxterm, need_cost: ($amount + $own),
    own_contribution: $own, free_cash: $free, minimum_cash: $cashmin,
    need_evidence: "VERIFIED_ESTIMATE", experience_years: $experience
  } |
  if $scenario == "d" then .scoring += {
    primary_income_source: "BUSINESS", net_monthly_income: 100000,
    qualification: "SPECIALIST", total_experience_months: 60,
    education_level: "HIGHER", car_class: "ECONOMY", real_estate_status: "NONE",
    buyer_contracts: "REPEAT_ORDERS", business_location: "VERIFIED_ONLINE_OR_MOBILE"
  } else . end' "data-collector/examples/scenario-$SCENARIO.json" > "$DEMO_DIR/questionnaire.json"

DEMO_FILES=()
if [ "$SCENARIO" = a ]; then
  DEMO_FILES=(-F 'files=@data-collector/examples/files/balance.pdf' \
              -F 'files=@data-collector/examples/files/balance.pdf.sig')
fi

curl --fail-with-body -sS -i "$DEMO_API/applications/$APPLICATION_ID/questionnaire" \
  -H "Authorization: Bearer $DEMO_TOKEN" \
  -F "questionnaire=<$DEMO_DIR/questionnaire.json" "${DEMO_FILES[@]}"

printf '\nЗаявка: %s\nКопия анкеты: %s/questionnaire.json\n' "$APPLICATION_ID" "$DEMO_DIR"
printf 'Открыть в кабинете: http://localhost:3000/applications/%s\n' "$APPLICATION_ID"
curl --fail-with-body -sS "$DEMO_API/applications/$APPLICATION_ID" \
  -H "Authorization: Bearer $DEMO_TOKEN" | jq .
)
```

Регистрация должна вернуть `201` для нового черновика либо существующий черновик того же автора и компании; отправка анкеты — `202`. Для просмотра в UI войти тем пользователем, от которого выполнен запрос; для A в этом примере это Литвинова.

После обработки проверить `GET /applications/{app_id}`, поле `collection_task_id` и `GET /collections/{task_id}`. Итоговые ручки: `GET /applications/{app_id}/decision`, `/offers`, `/info-requests`. У решения до оценки возможен `404`; это не тот же случай, что `502` от nginx.

Синтетическая дата mock-api и общего стека зафиксирована на **2026-10-22** (`DEMO_EVALUATION_DATE` у worker решений и scoring). В JSON согласия действуют до `2027-04-21`; при переносе демонстрации за пределы этого периода проверить сроки согласий. Для воспроизведения не менять дату оценки только у одного сервиса.

## 12. Финансовые документы: два отдельных backend-сценария

Это самостоятельный API обработки финансовых документов. Его не следует путать с обычным прикреплением `balance.pdf` к анкете.

| Сценарий | Контекст существующей заявки | Загрузка | Что извлекается |
|---|---|---|---|
| ИП на УСН «Доходы» | `financial_document_context.tax_regime = USN_INCOME` | КУДиР XLS/XLSX, тип `TAX_RETURN` | Налоговый доход |
| ООО | `financial_document_context.legal_form = OOO` | PDF ГИРБО, тип `FINANCIAL_STATEMENTS` | Выручка, прибыль, активы, капитал, обязательства |

Нужны миграции до `00008_financial_worker.sql`, общий `DOCUMENT_STORAGE_PATH` у API и worker, настоящий файл с ИНН соответствующего заёмщика. Контекст заполняется владельцем интеграции в `applications.form`; публичного API для установки этого контекста в текущем кабинете нет. Простая загрузка любого PDF не гарантирует финансовый результат.

HTTP-пути напрямую через `http://localhost:8081/api/v1`:

- `POST /applications/{id}/documents`: multipart `file`, `type`, необязательные `signatures`.
- `GET /applications/{id}/documents/{doc}/financial-result`: до готовности `202 PENDING`.
- `GET /applications/{id}/documents/{doc}/signature-report`: отдельный результат подписи.

Собственные локальные образцы называются `kudir-2026.xls`, `girbo-2025.pdf`, ожидаемые реквизиты задаются в `cases.json`; они не поставляются в Git. Подробный ввод и ограничения: [финансовые документы](financial-documents.md), [локальные образцы](../data-collector/financial_parser/testdata/README.md).

### 13.1. Отдельный административный кабинет credit-engine

В корневом Compose административный кабинет редактора моделей не запускается. Для него используется `credit-engine/compose.credit-engine.yaml`.

1. Из `credit-engine/` собрать образ: `docker build -t credit-engine:local .`.
2. Скопировать `config/admin.env.example` в локальный `.env.admin`.
3. Заполнить `CREDIT_ENGINE_NETWORK` — существующая сеть с PostgreSQL и поставщиками; `ADMIN_DATABASE_URL`; `STATEMENTS_URL` и, когда нужен модели, `FACTS_URL`.
4. Задать собственные `ADMIN_USERNAME`, bcrypt-хеш `ADMIN_PASSWORD_HASH` и общий секрет `ADMIN_EVENTS_TOKEN` для МС2/МС3. Предустановленной пары логин/пароль нет. Хеш создаёт `/admin-password` внутри образа; инструкция — в [README движка](../credit-engine/README.md). Хеш в env-файле заключить в одинарные кавычки из-за символов `$`.
5. Для локального HTTP: `ADMIN_PUBLIC_ORIGIN=http://localhost:8084`, `ADMIN_COOKIE_SECURE=false`. Если общий стек уже занимает 8082, добавить `SCORING_PORT=8085` в `.env.admin` либо остановить конфликтующий сервис.

```bash
docker compose --env-file .env.admin -f compose.credit-engine.yaml run --rm admin-migrate up
docker compose --env-file .env.admin -f compose.credit-engine.yaml up -d
```

Открыть [http://localhost:8084](http://localhost:8084) и ввести заданные на шаге 4 логин и исходный пароль. Сценарии: создать черновик версии → изменить критерии → сохранить ревизию → загрузить набор симуляции → сравнить расчёт → подготовить и скачать релиз; отдельно просмотреть сообщения МС2. Изменения черновика не переключают модель работающего скоринга без генерации, сборки и развёртывания.

## 14. Негативные сценарии и типичные проблемы

| Проверка | Ввод / условие | Что должно произойти |
|---|---|---|
| Неверный возраст | `17` | Анкета не отправляется, показана ошибка возраста |
| Неверный БИК | `1234` | Ошибка формата; корректный пример `044525225` |
| Неверный VIN | `XTC652005N149821O` с буквой O | Ошибка; корректный пример `XTC652005N1498213` |
| Неверная МЧД | `12345` | Ошибка UUID |
| Неприемлемые предпочтения | Максимальная ставка `150`; максимальный срок меньше запрошенного | Ошибки шага «Для оценки» |
| Повторная подпись к файлу в анкете | Оригинал + две привязываемые к нему откреплённые подписи | Ошибка текущего мастера анкеты; отдельный financial API имеет свой контракт |
| Нет согласий / источников | Не отмечать БКИ/налоги, не давать токены | Источники пропускаются с причиной; движок может запросить данные |
| Сбой сбора MSW | В полном мок-режиме оформить компанию с ИНН `7799000077` | Задача `FAILED`, UI показывает «Не получилось собрать данные о компании»; это специальный ИНН мока, не реального mock-api |
| Ошибка 502 у `/api/v1/applications` | Старая сборка продолжает обращаться к `http://api:8080` при выключенных моках | В стеке нет `api`; пересобрать актуальный frontend с отключёнными legacy-запросами либо включить `FRONTEND_API_MOCK=true` для старых демо-экранов и пересобрать |
| Опрос каждые 2 секунды | Есть заявка, по которой идут сбор/оценка/проверка подписи | Ожидаемое поведение data-collector UI; проверять статус, а не отключать опрос вслепую |
| Долго `SUBMITTED` | Не дошло событие или не работает обработчик | Проверить publisher, Kafka и worker |
| Долго `VERIFYING` / `SCORING` | Нет результата оценки | Проверить decision-worker и credit-engine; подписи могут ожидаться до `DECISION_SIGNATURE_WAIT` |
| Сбор `COMPLETED`, часть источников `SKIPPED` | Нет входов для конкретного источника | Посмотреть `reason`; это допустимое завершение сбора |
| Подпись имеет неопределённые полномочия | Нет завершённого сбора, корректной МЧД или данных руководителя | Смотреть этапы отчёта и входные данные, а не считать это ошибкой целостности файла |

Ошибки конкретного внешнего эмулятора можно проверить заголовком `X-Mock-Fault`: `500`, `503`, `timeout`, `captcha`. Заголовок задаётся в запросе **к mock-api**, на старый `/bank/v1` он не действует. Это не автоматический способ уронить всю заявку data-collector. Дополнительные субъекты стоп-проверок: ЮЛ `7799000099` — санкционный список; ФЛ `779900099018` — дисквалификация/паспорт. Они не являются полными наборами A–E.

## 15. Как повторить демонстрацию и что сохраняется

- Готовые заявки MSW меняют состояние после кликов: подписанную заявку нельзя снова показать как неподписанную без восстановления мока.
- Для возврата исходных **браузерных** демо-данных открыть DevTools → Console на адресе кабинета и выполнить:

  ```javascript
  localStorage.removeItem('credit-cabinet:mock-db:v10');
  localStorage.removeItem('credit-cabinet:collector-mock:v1');
  localStorage.removeItem('credit-cabinet:mock-fail');
  localStorage.removeItem('credit-cabinet:mock-pipeline-ms');
  location.reload();
  ```

- Это не удаляет записи PostgreSQL и документы настоящего backend. Черновики новой анкеты и файлы IndexedDB также имеют отдельное хранение; приведённая команда не является полным сбросом всех данных браузера.
- На живом backend незавершённый черновик автора по той же компании возвращается при повторной регистрации. Отправленные заявки сохраняются; можно создать следующий черновик через новую регистрацию.
- У data-collector после всех ответов клиента не обязательно возникает одобрение: повторная оценка может оставить ручной маршрут.
- Данные банка credit-engine и идемпотентных операций находятся в памяти его процесса. Перезапуск меняет исходные условия последующих расчётов. Для точного воспроизведения 17 эталонов использовать изолированную приёмку.
