# Финансовые документы MVP

Реализация находится в `data-collector/internal/financial` и `data-collector/financial_parser`.
Это внутренний backend API; авторизация пользователей, экран заявки и скоринговая модель
в этом модуле не реализованы. Документы привязаны к существующей строке `applications`.

## Два сценария

| Заёмщик | Контекст заявки | Тип загрузки | Данные |
|---|---|---|---|
| ИП | `tax_regime: USN_INCOME` | `TAX_RETURN`, XLS/XLSX КУДиР | `usn_taxable_income`, налоговый доход |
| ООО | `legal_form: OOO` | `FINANCIAL_STATEMENTS`, PDF ГИРБО | бухгалтерская выручка, прибыль, активы, капитал, обязательства |

Контекст хранится в `applications.form.financial_document_context`. Тип и ИНН заёмщика
берутся из `companies`, не из полей multipart. У ИП объект «Доходы» и ИНН дополнительно
сверяются с титулом КУДиР; у ООО — с содержимым PDF. Налоговый режим ООО не выводится
из его организационно-правовой формы и не ограничивается ОСНО.

```json
{"financial_document_context":{"tax_regime":"USN_INCOME"}}
```

Для ООО вместо `tax_regime` нужен `legal_form: OOO`. Контекст должен быть заполнен
существующим владельцем заявки до загрузки; отдельный публичный API редактирования
заявок в data-collector отсутствует. Неизвестный/неподдерживаемый контекст даёт 422
`UNSUPPORTED`, а не выбирает сценарий по длине ИНН.

## Запуск и API

Применить миграцию `00004_financial_documents.sql` через модуль `db`. API и worker
используют общий каталог `DOCUMENT_STORAGE_PATH` (по умолчанию `/data/documents`);
в compose для него добавлен постоянный volume `documents`.

Python-парсер включён в образ. При локальном запуске установить зависимости:

```bash
python3 -m pip install -r data-collector/financial_parser/requirements.txt
export FINANCIAL_PARSER_PATH="$PWD/data-collector/financial_parser/parser.py"
export DOCUMENT_STORAGE_PATH=/tmp/credit-documents
```

Все пути ниже имеют префикс `/api/v1`:

| Метод | Путь | Результат |
|---|---|---|
| POST | `/applications/{id}/documents` | multipart `file`, `type`, необязательные `signatures` (до двух); 201 |
| GET | `/applications/{id}/documents` | список метаданных |
| GET | `/applications/{id}/documents/{doc}` | метаданные, хеш, поколение, состояние подписи |
| GET | `/applications/{id}/documents/{doc}/content` | точные исходные байты |
| GET | `/applications/{id}/documents/{doc}/financial-result` | текущий результат, либо 202 `PENDING` |
| GET | `/applications/{id}/documents/{doc}/signature-report` | отдельный отчёт подписи, либо 202 |
| POST | `/applications/{id}/documents/{doc}/signature-verification` | новая проверка, 202 |

Отделённую подпись можно загрузить позже: `type=SIGNATURE`, `signed_document_id=doc_...`.
Нельзя привязать её к документу другой заявки. Загрузка разрешена в `DRAFT` и
`WAITING_FOR_INFO`. Оригинал и каждая подпись ограничены 20 МиБ.

Изменение документа — новая загрузка, старые байты не перезаписываются. Загрузка подписи
или повторная проверка увеличивает поколение оригинала. Пока новый результат не готов,
API не возвращает старый результат как актуальный. Результаты и отчёты подписи хранятся
отдельными строками. Присоединённое содержимое сохраняется отдельным объектом с хешем;
оно не подменяет загруженный контейнер.

Задача и outbox создаются в одной транзакции. Событие `financial.document.requested`
идёт через существующий топик Kafka. Worker различает финансовые задачи и сбор внешних
систем. Снимок подписей и контекст заявки фиксируются на поколение. Блокировка строки
задачи защищает от параллельного выполнения; повтор завершённой задачи не добавляет отчёты.

## Подключение валидатора коллеги

Криптография **не реализована** в этом изменении. Локальная граница:
`SignatureVerifier.Verify(ctx, VerifyInput) (SignatureReport, error)`.
По умолчанию используется адаптер к URL из `SIGNATURE_VERIFIER_URL`. Пустой URL,
таймаут, неполный/неподдерживаемый ответ дают `INDETERMINATE` и пустые `scoring_indicators`.

HTTP-адаптер отправляет POST JSON:

```json
{
  "document":"<base64 оригинальных байтов>",
  "document_sha256":"<sha256>",
  "signatures":["<base64 отделённой подписи>"],
  "applicant":{"applicant_type":"SOLE_PROPRIETOR","inn":"...","tax_regime":"USN_INCOME","legal_form":""},
  "policy":"KUDIR_IP"
}
```

Ответ — `SignatureReport` из OpenAPI, дополненный необязательными `signed_content`
(base64 точного подписанного содержимого присоединённого контейнера) и
`signed_content_sha256`. Полный ответ без бинарного содержимого сохраняется в `raw`.
Это предложенный интеграционный контракт: при отличии транспорта валидатора нужно
заменить HTTP-адаптер, не парсеры и не правила допуска.

Политики:

- `KUDIR_IP`: квалифицированная подпись самого ИП, ИНН ФЛ из сертификата = заёмщику,
  проверки `SIGNER_MATCHES_APPLICANT` и `SIGNER_AUTHORITY` пройдены.
- `GIRBO_FNS`: подтверждённый субъект сертификата — ФНС (ИНН 7707329152),
  `SIGNER_IS_FNS=PASSED`. ИНН организации в PDF сверяется отдельно.

Обе политики требуют `PASSED` для разбора, целостности, математики подписи, срока
сертификата, доверенной цепочки, аккредитации, статуса отзыва, квалифицированных
атрибутов и назначения ключа. Для PDF дополнительно требуется `DOCUMENT_NOT_MODIFIED`.
`VALID_WITH_WARNINGS` допускается только при выполнении всех этих обязательных проверок.
`MOCK`, `UNKNOWN`, `SKIPPED`, отсутствие обязательной проверки и несовпадение хеша
не допускают показатели. Политику нельзя ослабить параметром повторного запроса.

XLS/XLSX не считаются подписанными по факту расширения. Отображаемое имя «ФНС» и
сертификат, лишь выданный УЦ ФНС, не удовлетворяют политике ООО.

## Извлечение и пригодность

Парсер работает после вызова валидатора, в том числе диагностически при незавершённой
проверке. Он не выдаёт криптографический вердикт. XLS/XLSX читаются без офисных приложений;
макросы и внешние ссылки не выполняются. Формулы не вычисляются: их сохранённые значения
считаются непроверенными и блокируют допуск. Есть лимиты CPU, памяти, количества ячеек,
распакованного XLSX, страниц PDF и размера вывода процесса.

Деньги — `Decimal`, JSON — строки в рублях с двумя десятичными знаками. Явный ноль
отличается от пустоты, прочерка и многоточия. Координаты ячеек и PDF-областей сохраняются
вместе с исходным текстом. Показатели разных периодов не объединяются.

В `FinancialDocumentResult` разделены:

- `extracted`: исходные извлечённые данные, включая частичные/противоречивые;
- `signature`: проверка подписи, также доступная отдельной ручкой;
- `validation` и `diagnostics`: сверки данных и ошибки с источниками;
- `indicators`: кандидаты с `data_eligible`, итоговым `eligible` и причинами;
- `scoring_indicators`: только допущенные показатели.

Неполная детализация КУДиР блокирует налоговый доход даже при согласованных итогах.
Налоговый доход не превращается в бухгалтерскую выручку, чистую прибыль, рентабельность
или DSCR. Пустая графа расходов не означает нулевые расходы бизнеса.

Для PDF арифметические ошибки блокируют затронутые показатели и периоды. Если для
проверки не хватает строк, результат `NOT_CHECKABLE`, отсутствующие строки не
достраиваются нулями. Согласование чистой прибыли с налогом требует проверки;
неясная разница сохраняется как `NET_PROFIT_UNRECONCILED`, без исправления отчётности.

## Реальные образцы и проверки

Реальные XLS/PDF хранятся только локально и исключены из Git и Docker build context.
Для запуска проверок положите копии в `data-collector/financial_parser/testdata`
либо задайте `FINANCIAL_FIXTURES_DIR` (абсолютный путь к каталогу с указанными ниже именами).
Без файлов проверки реальных документов пропускаются; синтетические тесты выполняются.
Это образцы извлечения, не фикстуры успешной ЭП.

| Образец | Проверенные значения |
|---|---|
| `kudir-2026.xls` | 2026, «Доходы»; 4 операции на 360 000 ₽; возврат −126 000 ₽; I квартал 1 755 000 ₽; год и сумма кварталов 6 355 000 ₽ |
| `girbo-2025.pdf` | ИНН и контрольные суммы из локального `cases.json`; отдельные периоды, масштаб сумм и отрицательные значения |

КУДиР: многоточия, пустая справка 010–041, частичные суммы операций, согласованные
накопительные итоги. Доход не допущен. PDF: чистая прибыль не согласована с прибылью
до налога и налогом; суммы сохранены, чистая прибыль заблокирована.

```bash
cd data-collector
python3 -m unittest discover -s financial_parser/tests -v
FINANCIAL_REAL_TESTS=1 go test ./internal/financial -v
go test ./...
go vet ./...
# PostgreSQL-тест создаёт отдельную схему, применяет миграции и удаляет её после теста:
FINANCIAL_TEST_DATABASE_URL='postgres://.../test?sslmode=disable' \
  FINANCIAL_REAL_TESTS=1 go test -tags integration ./internal/financial -v
```

Проверены несовпадение ИНН, XLSX-вариант образца со вставленными строками, отрицательные
числа и явные нули, формула без надёжного результата, повторная доставка, поздняя подпись,
сохранение истории и изменение сохранённых байтов. Изменение файла обнаруживается по
контрольному хешу; криптографическая проверка изменённого подписанного файла и реальной
подписи ФНС остаётся интеграционной проверкой после предоставления настоящего валидатора.
