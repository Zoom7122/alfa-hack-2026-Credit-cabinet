# Проверка электронных подписей

Зачем это нужно в конвейере:

1. **Документы клиента.** Бухотчётность, доверенности, договоры с контрагентами часто приходят подписанными КЭП. Подпись подтверждает, что документ настоящий и не изменён, — это сильнее любого распознавания.
2. **Полномочия представителя.** Заявку может подать любой уполномоченный сотрудник, и его полномочия подтверждаются машиночитаемой доверенностью (МЧД), подписанной директором.
3. **Подписание кредитного договора.** Подписывает только директор: проверяем, что подпись его, сертификат действующий, а ИНН/ОГРН в сертификате совпадают с компанией-заявителем.

## Виды подписи (63-ФЗ)

| Вид | Что это | Как используем |
|---|---|---|
| ПЭП (простая) | код/пароль; значима только по соглашению сторон | `SIMPLE_CODE` в кабинете (код показывается в UI, SMS по ТЗ нельзя) |
| НЭП (неквалифицированная) | криптоподпись, сертификат не от аккредитованного УЦ | распознаём, вердикт не выше `VALID_WITH_WARNINGS`, полномочий не даёт |
| **КЭП (квалифицированная)** | сертификат аккредитованного УЦ, ГОСТ Р 34.10-2012 | основной сценарий: документы, МЧД, договор |

Кто чем подписывает сейчас:
- **Руководитель ЮЛ и ИП** — КЭП, выданная УЦ ФНС. В сертификате есть ИНН ЮЛ и ОГРН (для ИП — ОГРНИП).
- **Сотрудники** — личная КЭП физлица + МЧД от организации. Переходный период для старых «сертификатов сотрудника» закончился 31.08.2024; МЧД в формате ФНС 5.02 хранится в распределённом реестре.

> Сроки и форматы МЧД перед защитой надо сверить с актуальными разъяснениями ФНС/Минцифры. Найденные материалы относятся к 2023–2024 годам.

## Форматы, которые принимает ручка

| Контейнер | Формат | Как приходит |
|---|---|---|
| CMS / PKCS#7 | CAdES-BES, CAdES-T (с меткой времени), CAdES-X Long Type 1 (с данными об отзыве) | `.sig` / `.p7s` открепленная к файлу или присоединённая (документ внутри) |
| PDF | PAdES (подписи внутри PDF, может быть несколько) | `.pdf` |
| XML | XMLDSig / XAdES (так устроены МЧД и отчётность в ФНС) | `.xml` |

Один документ может нести **несколько подписей**: несколько `SignerInfo` в CMS, несколько PAdES-подписей в PDF, подпись директора + квитанция ФНС. Проверяем каждую и отдельно считаем, выполнена ли **политика** — набор подписей, обязательных для этого типа документа.

## Чек-лист проверки одной подписи

| # | Код проверки | Что проверяем | Провал → |
|---|---|---|---|
| 1 | `FORMAT_PARSED` | контейнер разбирается, найдены SignerInfo и сертификат | INVALID |
| 2 | `INTEGRITY` | хэш документа (ГОСТ Р 34.11-2012) совпадает с `messageDigest` в подписи | INVALID |
| 3 | `SIGNATURE_VALUE` | математика подписи по открытому ключу сертификата | INVALID |
| 4 | `DOCUMENT_NOT_MODIFIED` | для PDF: после подписи нет инкрементальных изменений, кроме разрешённых | INVALID |
| 5 | `CERT_VALID_AT_SIGNING_TIME` | время подписи попадает в срок действия сертификата | INVALID |
| 6 | `SIGNING_TIME_TRUSTED` | время взято из метки TSP (CAdES-T и выше), а не только из `signingTime` подписанта | WARNING |
| 7 | `CHAIN_TO_TRUSTED_ROOT` | цепочка строится до доверенного корня (Головной УЦ Минцифры) | INVALID |
| 8 | `ISSUER_ACCREDITED` | выдавший УЦ был аккредитован на момент подписи (перечень Минцифры, TSL) | НЭП, WARNING |
| 9 | `NOT_REVOKED` | сертификат не отозван на момент подписи: OCSP из AIA или CRL из CDP; для XLT1 — по вложенным данным | INVALID; не удалось проверить → INDETERMINATE |
| 10 | `QUALIFIED_ATTRIBUTES` | есть обязательные для КЭП расширения: `subjectSignTool` 1.2.643.100.111, `issuerSignTool` 1.2.643.100.112, политики КС1/КС2 | НЭП, WARNING |
| 11 | `KEY_USAGE` | `digitalSignature` / `nonRepudiation` | INVALID |
| 12 | `SIGNER_MATCHES_APPLICANT` | ИНН ЮЛ (1.2.643.100.4) / ОГРН (1.2.643.100.1) / ОГРНИП (1.2.643.100.5) из сертификата = заявителю | по политике |
| 13 | `SIGNER_AUTHORITY` | подписант — действующий руководитель по ЕГРЮЛ (сверка ФИО + ИНН ФЛ 1.2.643.3.131.1.1 / СНИЛС 1.2.643.100.3), ИП — сам ИП, иначе нужна МЧД | по политике |
| 14 | `POA_VALID` | МЧД: подпись доверителя (рекурсивно этим же чек-листом), срок действия, не отозвана в реестре ФНС, представитель = подписант, нужное полномочие есть в списке | по политике |

Итоговый вердикт подписи (термины как в ETSI): `VALID` · `VALID_WITH_WARNINGS` · `INVALID` · `INDETERMINATE` (криптография в порядке, но нет данных для заключения — например, OCSP/CRL недоступны).

Вердикт документа = худший из вердиктов **обязательных** подписей + `policy.satisfied`.

## Политики

| `policy` | Обязательные подписи | Где применяется |
|---|---|---|
| `GENERIC` | хотя бы одна валидная подпись | любой загруженный документ |
| `POWER_OF_ATTORNEY` | КЭП руководителя доверителя (`SIGNER_AUTHORITY` = HEAD), ИНН доверителя = заявитель | документ `POWER_OF_ATTORNEY`, когда заявку подал не директор |
| `FINANCIAL_STATEMENTS` | КЭП руководителя или подписанта по МЧД + (опционально) квитанция ФНС | `FINANCIAL_STATEMENTS`, `TAX_RETURN` |
| `LOAN_CONTRACT` | КЭП руководителя заявителя (или ИП) **по сгенерированному банком договору** (хэш = хэш нашего PDF) | `signing/confirm` с `QUALIFIED_SIGNATURE` |

## Как встраивается в процесс

- **Загрузка документа.** Если файл содержит подпись или пришёл `.sig` с `signed_document_id`, автоматически ставится pgqueue-таска `signature.verify`, потому что OCSP/CRL — сетевые запросы. Результат: `Document.signatures` и WS-событие `document.signatures_verified`.
- **VERIFYING.** Документы с `VALID` повышают доверие к цифрам из распознавания: например, подписанная бухотчётность закрывает расхождение `REVENUE_MISMATCH` без вопросов клиенту. `INVALID` по доверенности → info-request «загрузите действующую доверенность».
- **SIGNING → COMPLETED.** Переход разрешён, только если вердикт по политике `LOAN_CONTRACT` — `VALID` или `VALID_WITH_WARNINGS`. `INVALID` → `SIGNING → OFFERED` (`sign.failed`). `INDETERMINATE` → повторить проверку позже, заявка остаётся в `SIGNING`.
- **Back-office.** Видит полный отчёт по каждой подписи и может перезапустить проверку.
- **Отдельная ручка `POST /signatures/verify`.** Проверка без привязки к заявке: «проверь этот файл». Пригодится и клиенту (самопроверка перед загрузкой), и сотруднику.

## Реализация

```go
type SignatureVerifier interface {
    Verify(ctx context.Context, in VerifyInput) (SignatureReport, error)
}
```

- **Хакатон.** Отдельный контейнер `sigverify` (Go + OpenSSL 3 с `gost-engine`/`gost-provider`, open source) разбирает CMS/PAdES/XMLDSig и проверяет ГОСТ-подписи. Trust store в режиме `mock` — наш тестовый корневой УЦ (ГОСТ-ключи генерируются в сидах, им же выпускаются КЭП синтетических директоров + локальный CRL). В режиме `live` — корни Минцифры и перечень аккредитованных УЦ (TSL с e-trust.gosuslugi.ru), OCSP/CRL из сертификата с кэшем. МЧД в `mock` проверяется по локальной таблице, в `live` — через реестр ФНС.
- **Прод.** Юридически значимая проверка КЭП требует сертифицированного ФСБ СКЗИ (КриптоПро и т.п.). Это платформенный сервис банка, который подключается через тот же интерфейс, — так и говорим на защите. В `THIRD_PARTY_NOTICES` указываем gost-engine и то, что УЦ/реестр МЧД смоделированы.

## Демо-сценарии (сиды)

| Сценарий | Ожидание |
|---|---|
| Договор подписан КЭП директора «Ромашки» | `VALID`, заявка → COMPLETED |
| Договор подписан КЭП бухгалтера без МЧД | `INVALID` (`SIGNER_AUTHORITY`), → OFFERED |
| Доверенность подписана директором, срок истёк | `INVALID` (`POA_VALID`), info-request |
| PDF изменён после подписания | `INVALID` (`DOCUMENT_NOT_MODIFIED`) |
| Сертификат отозван (есть в тестовом CRL) | `INVALID` (`NOT_REVOKED`) |
| OCSP/CRL недоступны (выключен мок УЦ) | `INDETERMINATE` |
| Подпись самоподписанным сертификатом | `INVALID` (`CHAIN_TO_TRUSTED_ROOT`) |
